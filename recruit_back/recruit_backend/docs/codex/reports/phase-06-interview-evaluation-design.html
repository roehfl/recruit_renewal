Phase 06 - 면접 평가 설계

설계 완료 작성일: 2026-05-27 (등급 체계 반영: 2026-05-28)

요약

Phase 06은 면접 평가 도메인을 설계합니다. 각 면접관이 확정된 면접에서 후보자별로 등급을 부여하고 추천 의견을 제출합니다.

이 설계에서 InterviewEvaluation은 평가 근거 자료이며, 최종 합격/불합격 결정인 StageResult와 엄격히 분리됩니다. 면접관의 제출은 StageResult를 절대 변경하지 않습니다.

관리자가 평가 행을 초기화하고, 면접관이 평가를 저장/제출하며, 관리자가 그룹별 요약을 조회합니다. 기존 StageResult 수정/일괄수정 API가 최종 결과 확정의 유일한 경로로 유지됩니다.

구현은 5개 slice로 분할됩니다: 도메인(06a), 초기화 + 면접관 입력(06b), 관리자 조회(06c), 재개 + 경계(06d), 안정화(06e).

상태 전이

EvaluationStatus 생애주기

(초기화) → DRAFT → (저장) → DRAFT → (제출) → SUBMITTED
SUBMITTED → (관리자 재개) → DRAFT → (재제출) → SUBMITTED

재개 시 submittedAt이 초기화됩니다. 재개 이력은 별도 엔티티 필드가 아닌 ActivityLog에 기록됩니다.

StageResult 경계 정책

핵심 정책 비변경 보장

  • InterviewEvaluation은 평가 근거 자료이며, 최종 전형 결과가 아닙니다.
  • StageResult가 최종 결정 레코드(PASS/FAIL/PENDING)로서 유일합니다.
  • 면접관의 submit은 StageResult를 생성, 수정, 발표, 정정, 게시하지 않습니다.
  • InterviewEvaluation의 엔티티, 서비스, 컨트롤러는 StageResultRepository 또는 StageResultService를 주입하거나 호출하지 않습니다.
  • 자동 또는 반자동 StageResult 반영 커맨드는 Phase 06에 포함되지 않습니다.

관리자 워크플로우

  1. 확정된 면접에 대해 평가 행을 초기화합니다.
  2. 면접관들이 평가를 제출할 때까지 대기합니다.
  3. 관리자 조회 API를 통해 평가 요약을 확인합니다.
  4. 기존 POST /admin/stages/{stageId}/results/{resultId} 또는 .../results/bulk를 사용하여 수동으로 최종 결과를 확정합니다.

전용 반영 커맨드(예: reflect-interview-evaluations)는 향후 Phase로 명시적으로 연기되었습니다.

면접관 정보 격리

면접관은 본인의 평가만 조회할 수 있습니다. 다른 면접관의 등급, 추천 의견, 코멘트, 제출 상태를 볼 수 없습니다. 이는 평가의 독립성을 보장하고 편향을 방지하기 위함입니다.

#결정근거
1후보자와 면접관 모두 InterviewParticipant FK 사용대칭적 설계, 기존 모델과 일관성, 가드 체크 단순화

3초기화와 면접 확정을 분리다른 관심사: 일정 vs 평가 준비
