Phase 04 - Interview Scheduling Design

Design Completed Generated: 2026-05-26

Executive Summary

Phase 04 is defined as Interview Scheduling, not a DB-operations baseline phase.

The design introduces Interview and InterviewParticipant as the schedule and assignment model for candidates and interviewers.

The responsibility is limited to who attends which interview, when, where, and in which group. Interview Scheduling must not become an alternative result announcement channel.

Interview scoring, result publication, messaging, Excel, PDF, and frontend work are excluded. Admin confirmation may read StageResult only to verify candidate eligibility; applicant schedule reads do not expose or mutate StageResult.

The next implementation can start with a domain slice while keeping StageResult unchanged.

Architecture Domain

Interview

Entity Candidate

Owns schedule, group, time range, method, place, online meeting URL, admin memo, and lifecycle status.

  • Connected to JobPosting and Stage.
  • Allowed stage types: FIRST_INTERVIEW, SECOND_INTERVIEW, FINAL_INTERVIEW.
  • Allowed stage statuses for creation/confirmation: READY, IN_PROGRESS.
  • Status: DRAFT, CONFIRMED, CANCELLED.
  • groupName is required; single-group interviews can use a default such as 1조.

InterviewParticipant

Entity Candidate

Owns assignment rows for both candidates and interviewers.

  • CANDIDATE: requires jobApplication, no employee.
  • INTERVIEWER: requires employee, no jobApplication.
  • First implementation uses ASSIGNED; CANCELLED is reserved for later partial participant cancellation/amendment.
  • DRAFT replacement may delete and recreate participant rows.
  • Schedule cancellation keeps existing participants ASSIGNED.
JobPosting
  └─ Stage
      └─ Interview
          ├─ InterviewParticipant(CANDIDATE) -> JobApplication -> Applicant
          └─ InterviewParticipant(INTERVIEWER) -> Employee

StageResult remains separate and is not mutated by Interview Scheduling.

Validation Rules

Confirmation Guards

  • At least one assigned candidate.
  • At least one assigned interviewer.
  • Valid time range.
  • Same job posting and stage ownership.
  • Candidate eligibility before admin confirmation.
  • No duplicate assignment or confirmed schedule collision.

Stage Guards

  • Stage type must be FIRST_INTERVIEW, SECOND_INTERVIEW, or FINAL_INTERVIEW.
  • Creation and confirmation require stage status READY or IN_PROGRESS.
  • RESULT_ANNOUNCED and CLOSED reject creation, participant replacement, and confirmation.
  • Cancellation is allowed until the stage becomes CLOSED.

Candidate Eligibility

  • Application must belong to the same posting.
  • Application status must be SUBMITTED.
  • If there is a previous stage, the candidate must have passed it.
  • Applicant-visible schedules require confirmed/cancelled status, owned candidate assignment, and no StageResult field exposure.

Collision Check

  • Target Interview.status = CONFIRMED.
  • Target participantStatus = ASSIGNED.
  • Same candidate application or same interviewer employee.
  • Exclude the current interview itself.
  • Overlap: existing start < requested end and requested start < existing end.
  • Ignore CANCELLED schedules.

Participant Lifecycle

  • DRAFT replacement may delete and recreate rows.
  • Confirmed schedule cancellation changes only Interview.status.
  • Existing participant rows remain ASSIGNED.
  • InterviewParticipantStatus.CANCELLED is reserved for a later partial cancellation/amendment phase.

Status Rules

  • DRAFT can update and replace participants.
  • DRAFT can become CONFIRMED.
  • CONFIRMED can become CANCELLED.
  • CONFIRMED participant replacement is rejected.
  • CANCELLED is terminal for the first slice.

Method Rules

IN_PERSON requires location. ONLINE requires online meeting URL. HYBRID requires both. OTHER allows a free-form policy.
