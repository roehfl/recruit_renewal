지원서 폼 레이아웃 — 관리자 화면 시안

공고별 지원서 섹션을 페이지로 그루핑하고 순서를 정하는 관리자 화면. 백엔드 API는 이미 구현되어 있으며, 시안은 그 계약을 그대로 만족하도록 설계했다.

GET · POST /admin/job-postings/{id}/application-form-layout GET .../preview 2026-09-02

확정 (2026-09-02)

시안 A(팔레트 + 페이지 캔버스)로 확정되었다. 확정된 정보 구조·API 계약·구현 slice 계획은 설계 보고서 docs/archive/reports/admin-application-form-settings_design.html가 단일 출처다. 이 문서는 시안 비교 기록으로 남긴다.

1. API가 강제하는 제약 (모든 시안 공통 전제)

ApplicationFormLayoutValidator · ApplicationFormLayoutService에서 읽어낸 불변식이다. 화면 설계는 이 5가지를 어길 수 없다.

  • 1배치된 섹션 집합 == 활성 섹션 집합. 활성인데 안 놓아도, 비활성인데 놓아도 저장 실패다(placedSections.equals(effectiveEnabledSections)). 즉 "미배치 서랍"에 뭔가 남은 상태로는 저장할 수 없다.
  • 2섹션의 사용/필수 여부는 이 화면에서 못 바꾼다. 학력·경력 등은 공고 등록/수정 화면의 ApplicationFormConfig, 자기소개서는 질문 등록 여부, 첨부는 첨부요구 행에서 파생된다(availableSections[].source). 이 화면은 그루핑 + 순서만 다룬다.
  • 3페이지는 최소 1개, 각 페이지는 항목 최소 1개. 제목 필수(100자), 설명 500자, pageNo·페이지 sortOrder는 중복 불가, 항목 sortOrder는 페이지 내 중복 불가.
  • 4저장은 전체 치환(POST 1회). 페이지 단위 부분 저장 API가 없다 — 화면 전체를 한 번에 보내고 서버가 delete 후 재삽입한다. 낙관적 잠금도 없다.
  • 5편집 가능 조건: 접수 시작 전 & 마감 아님. editable=false면 읽기 전용이어야 한다. 또 layoutStored=false면 지금 보이는 건 저장된 값이 아니라 기본 레이아웃 초안이므로 그렇게 표시해야 한다.
부가 발견 — 백엔드 sectionName은 영문("Basic Info", "Questions")이라 프론트에서 한글 라벨 매핑이 필요하다. 그리고 활성 섹션이 늘어난 뒤(예: 질문 추가) 기존 저장 레이아웃은 제약 1을 위반하게 되므로, 화면 진입 시 "새 섹션이 생겨 재배치가 필요합니다" 안내가 세 시안 모두에 필요하다.

추천 — C(우선) / B(차선). 이 API의 최대 함정은 "활성 = 배치" 불변식이라 저장 시점에 400이 나기 쉬운 것인데, C는 그 상태 자체를 만들 수 없게 한다. 페이지 순서 변경이 자주 필요하다는 요구가 있으면 B가 낫다. A는 조작감은 가장 좋지만 섹션 10개 규모에 DnD 도입 비용이 커서 후순위로 본다.

3. 시안 선택과 별개로 확인이 필요한 항목

  • 화면 진입 경로공고 상세에 탭으로 붙일지, 공고 수정 화면의 마지막 단계로 붙일지, 별도 라우트(/admin/job-postings/:id/form-layout)로 둘지. 섹션 사용여부(공고 수정)와 그루핑(이 화면)이 나뉘어 있어 왕복이 생긴다.
  • 접수 시작 후 진입 시editable=false. 화면 전체를 읽기 전용으로 할지, preview API 화면으로 리다이렉트할지.
  • 미저장 기본 레이아웃layoutStored=false일 때 자동 저장할지, 배지만 띄우고 관리자가 저장을 눌러야 확정할지.
  • 섹션 한글 라벨백엔드가 영문 sectionName을 주므로 프론트 상수로 매핑한다(sectionType 기준). 백엔드를 한글로 바꿀지 여부.
