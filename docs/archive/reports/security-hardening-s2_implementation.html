요약

전 시스템 보안 점검의 2차로, 공격 횟수 제한·첨부 내용 검사·CSRF 방어·기본 인가 정책 전환을 구현했습니다.

로그인과 이메일 인증번호는 세션과 무관하게 아이디·이메일 기준으로 셉니다. 병렬 세션으로 인증번호를 대입하던 경로와 사내 AD 계정 대입 경로를 막았습니다.

첨부는 확장자별 매직바이트를 확인합니다. /api POST는 X-Requested-With 헤더를 요구합니다. 매처에 없는 경로는 이제 공개가 아니라 인증 필수입니다.

보안 설정 규칙이 늘어 auth-account 카드가 상한을 넘게 되어, 새 카드 auth-security로 분리했습니다.

4첨부 내용 미검증(확장자·클라이언트 MIME만 비교)AttachmentSignatureValidator: pdf·jpg·png·OLE2(doc·xls·hwp)·ZIP(docx·xlsx·hwpx)·HWP 3.0 시그니처. 모르는 확장자는 거부Medium

결정 로그

#결정근거
1CSRF는 토큰이 아니라 커스텀 헤더 검사개발 환경에서 프론트·API 출처가 달라 axios가 XSRF 쿠키 토큰을 자동으로 붙이지 않습니다. 헤더 방식은 CORS 허용 목록과 맞물려 같은 효과를 내고 변경이 작습니다
2IP 기준 제한은 두지 않음프록시 헤더 처리가 없어 모든 요청 IP가 프록시 주소로 보입니다. IP 한도는 곧 전체 한도가 됩니다
3한도는 설정값으로 두고, 테스트 yaml은 크게한 Spring 컨텍스트에서 같은 계정·이메일을 여러 테스트가 쓰므로 공유 카운터에 걸립니다. 한도 동작은 단위 테스트가 검증합니다
4MockMvc 테스트에서는 CSRF 필터를 끔(recruit.csrf.header-required=false)기존 컨트롤러 테스트의 POST가 헤더를 붙이지 않습니다. 필터는 CsrfHeaderFilterTest와 실기동으로 검증했습니다. 로컬 Swagger POST에도 같은 스위치를 씁니다
5맵 상한 초과 시 fail-closed기존 ClientEventRateLimiter와 같은 방식입니다. 상한 100,000이라 채우려면 짧은 시간에 10만 건의 서로 다른 실패가 필요합니다
6주소·학교·코드 조회는 공개 유지이번 단계는 기본 정책만 전환하고 기존 공개 동작은 바꾸지 않았습니다. 모두 로그인 후 화면에서만 쓰여 로그인 필수화는 후속 후보입니다
7보안 설정을 새 카드 auth-security로 분리auth-account가 40KB 상한을 넘게 되어 카드 규칙(하위 도메인 분리)을 따랐습니다. 인가 표·CORS·CSRF·쿠키·시도 제한을 옮겼습니다
