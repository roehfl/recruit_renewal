요약

관리자가 지원자 공지사항을 직접 등록·수정·삭제할 수 있는 화면(/admin/notices)을 디자인 목업부터 백엔드·프론트 구현까지 완료했다.

핵심 결정은 노출 여부와 삭제를 하나의 상태로 합친 것이다. 별도 visible 필드 없이 deleted 하나만 두고, 삭제(soft delete)하면 지원자 화면에서만 사라지고 관리자 목록에는 "삭제됨"으로 남아 복구할 수 있다.

관리자 조회는 /admin/notices, 쓰기는 /board/notices로 나눴다. /board 아래 GET은 공개라 조회만 /admin으로 뺐고, 쓰기는 기존 POST /api/board/** 매처가 이미 관리자 전용으로 막고 있어 보안 설정을 건드리지 않았다.

본문 편집기는 새 의존성 없이 contenteditable + document.execCommand로 만들었고, 서버 정제(jsoup Safelist.relaxed())가 남기는 태그만 생성한다.

왜 필드를 하나로 합쳤는가

설계 결정

초기 설계에는 "지원자 화면 노출(visible)"과 "삭제(deleted)"가 따로 있었다. 두 필드를 두면 상태 조합이 4가지가 되고, 관리자 입장에서 "내려두기"와 "삭제"의 차이를 설명하기 어렵다.

실제로 필요한 동작은 지원자 화면에서 내리기 하나뿐이고, 그게 곧 soft delete다. 그래서 필드를 하나로 합치고 화면 라벨도 "삭제(Soft delete)"로 통일했다.

FAQ 도메인은 같은 개념을 active(반대 방향)로 쓴다. 이름이 다른 이유는 FAQ 화면 라벨이 "노출/비노출"이기 때문이며, 의미는 동일하다.

상태 전이

정상 흐름

없음 → POST /board/notices → 정상 (deleted=false) → POST /board/notices/{id}/delete → 삭제됨 (deleted=true)

복구 흐름

삭제됨 → POST /board/notices/{id}/restore → 정상

두 전환 모두 멱등이다. 이미 같은 상태면 그대로 200을 돌려준다. 없는 id는 404다. pinned는 이 전이와 독립이며 /pin·/unpin으로 따로 바꾼다.

결정 로그

#결정근거
1 노출 필드를 두지 않고 deleted 하나로 합친다 실제 필요한 동작은 "지원자 화면에서 내리기" 하나뿐이다. 두 필드는 상태 조합만 늘리고 운영자에게 설명하기 어렵다
2 관리자 조회는 /admin/notices, 쓰기는 /board/notices /board 아래 GET은 permitAll()이라 관리자 조회를 두면 공개된다. 쓰기는 기존 POST /api/board/** 매처가 이미 막고 있어 SecurityConfig 변경이 필요 없다
3 관리자 편집용 상세도 sanitize해서 내려준다 관리자 에디터도 HTML을 그대로 렌더한다. 정제가 멱등이라 원본 손실 없이 저장형 XSS만 막는다
4 고정 전환을 수정 API에서 분리해 /pin·/unpin으로 만든다 수정 API는 title·content가 필수라 목록에서 고정만 바꾸려면 상세를 먼저 받아야 한다. 건당 2회 호출이 되고 일괄 처리에서는 그 2배가 된다
5 본문 에디터를 외부 라이브러리 없이 만든다 프론트 AGENTS.md가 불필요한 의존성 추가를 금지한다. 서버가 허용 태그를 좁게 제한하므로 필요한 기능이 적고, contenteditable로 충분하다
6 일괄 처리는 FE가 건별로 호출하고 Promise.allSettled로 집계한다 일괄 API를 새로 만들 만큼 건수가 많지 않다. 부분 실패해도 나머지는 반영되고 실패 건수를 알린다
7 관리자 목록에 작성자 열을 넣지 않는다 AuditorAware 빈이 없어 createdBy가 항상 null이다. 지금 도입하면 모든 엔티티의 감사 컬럼이 동시에 채워지기 시작하므로 별도 결정 사항이다

미결 사항

#질문현재 입장
1 작성자를 화면에 표시할 것인가? 표시하려면 AuditorAware 도입이 먼저다. 모든 엔티티에 영향이 가므로 별도 결정 사항으로 남긴다. API는 필드를 이미 내려주고 있다
2 운영 DB의 ddl-auto 설정은? validate/none이면 docs/ops/notice-deleted-column.sql을 수동 반영해야 한다. 적용 전 백업을 권장한다
3 공지 첨부파일이 필요한가? 이번 범위에서 제외했다. 필요하면 별도 도메인 설계가 필요하다
4 document.execCommand 대체가 필요한가? 표준에서 deprecated지만 대체 표준이 없고 주요 브라우저가 모두 지원한다. 지원이 끊기면 에디터 컴포넌트만 교체하면 된다

다음 단계 권장

배포 전

  1. 운영 DB에 notice.deleted 컬럼 DDL 반영(docs/ops/notice-deleted-column.sql). 엔티티 정의와 컬럼 타입을 사람이 대조한다.
  2. 기존 공지는 전부 deleted=0으로 backfill된다. 내려둘 공지가 있으면 배포 후 화면에서 삭제 처리한다.

배포 후

  1. /admin/menus에서 공지사항 관리(/admin/notices) 메뉴를 등록한다(role-menu 카드).
  2. 관리자 계정으로 등록·수정·삭제·복구·고정을 한 번씩 확인한다. 특히 삭제 후 지원자 공지 목록에서 사라지는지 확인한다.
  3. 본문에 표·링크·이미지를 넣어 저장한 뒤, 지원자 상세에서 서식이 유지되는지 확인한다.
