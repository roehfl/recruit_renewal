지원자 로그인 2차 인증(NICE) 설계

설계 완료 구현 대기 작성일: 2026-10-08

요약

지원자 로그인에 NICE 본인확인을 2차 인증으로 붙입니다. 로그인 버튼을 누르면 NICE 팝업이 뜨고, 인증이 끝난 경우에만 POST /auth/login이 호출됩니다.

프론트만으로는 API 직접 호출로 우회되므로 서버가 세션의 NICE 결과와 계정 명의(Applicant.ciHash)를 대조합니다. 대조는 RoutingAuthenticationProvider의 지원자 분기에서 비밀번호 검증 직후에 합니다.

설정 recruit.nice.login-two-factor-enabled로 켜고 끕니다(기본 켜짐). 임직원(LDAP)은 적용 대상이 아닙니다.

구현은 백엔드 → 프론트 순서의 한 슬라이스로 진행합니다.

로그인 흐름

LoginView  로그인 클릭
  ├ 입력 비어 있음 → 중단
  ├ 2FA 꺼짐 또는 임직원(loginId에 @ 없음) → 바로 POST /auth/login
  └ 2FA 켜짐 + 지원자
       → window.open('/nice-auth?purpose=LOGIN')     (클릭 핸들러 안에서 동기 호출)
       → 팝업: /auth/nice/request → NICE 표준창 → 콜백 → /auth/nice/result
               세션 NICE_VERIFIED = { purpose=LOGIN, name, birth, gender, verifiedAt }
               postMessage(SUCCESS)
       → LoginView  SUCCESS 수신 → POST /auth/login

AuthController.login
  ├ 세션의 NICE_VERIFIED(purpose=LOGIN)를 토큰 details에 담음 (아직 지우지 않음)
  ├ authenticationManager.authenticate
  │    RoutingAuthenticationProvider
  │      ├ 시도 제한(429) → 비밀번호 검증 (기존)
  │      └ Applicant + 2FA 켜짐 → LoginSecondFactorVerifier.verify
  │           ① 결과 없음  ② 5분 초과  ③ identityHash ≠ applicant.ciHash
  └ 성공 또는 LoginSecondFactorException → 세션 결과 제거 / 비밀번호 실패 → 유지

NICE 결과는 서버 세션에만 있고 브라우저로 내려가지 않습니다. 세션 고정 방어(changeSessionId)는 속성을 옮기므로 Provider가 인증 전 세션 값을 읽는 데 문제가 없습니다.

결정 로그

#결정근거
1NICE 먼저, 로그인 제출은 그 뒤요청된 순서. 비밀번호 먼저 방식은 로그인 API가 2단계가 되어 채택하지 않음
2서버가 Provider에서 강제 (successHandler·프론트 아님)Provider 예외는 인증 실패로 처리되어 세션·SecurityContext가 만들어지지 않고 시도 제한이 센다
3비밀번호 실패 시 NICE 결과 유지, 유효 5분오타마다 재인증하면 과금·불편이 크다. 공격자는 명의 대조에서 막히고 비밀번호 시도는 한도가 막는다
42차 인증 실패 응답은 400 + 사유 문구휴대폰 변경의 명의 불일치와 같은 형태. 401은 세션 만료로 해석되는 경로가 있어 구분
5설정 기본값 켜짐, 끄면 NICE 없이 로그인보안 통제는 fail-closed. 로컬·NICE 장애 시 재기동으로 우회
6프론트는 GET /auth/login-options로 설정을 읽음팝업을 띄울지 알아야 하며 서버가 어차피 강제하므로 조회 실패 시 켜짐으로 간주
7로그인 이력 테이블은 만들지 않음요청 범위 밖. 사유 코드 로그만 남김
