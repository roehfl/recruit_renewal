NICE 본인확인 실연동 — 가입 흐름

구현 완료 실인증 검증 대기 2026-09-21

요약

지원자 가입 시 본인확인을 프론트 목업에서 NICE 체크플러스 실연동으로 바꿨다. 이전에는 프론트가 crypto.randomUUID()로 만든 가짜 CI를 서버가 그대로 믿어, 본인 확인이 사실상 없었고 ciHash 중복 차단도 무의미했다.

이제 서버가 NICE 응답을 복호화해 얻은 CI만 쓰며 CI는 브라우저로 한 번도 내려가지 않는다. NICE 콜백은 cross-site POST라 세션 쿠키가 없으므로, 콜백은 REQ_SEQ로만 찾고 세션 대조는 뒤따르는 same-site 요청으로 미뤘다.

최종 코드 리뷰가 순차 테스트로는 안 보이던 동시성 결함 3건을 재현했고, 벤더 모듈 실측으로 EUC-KR 규격·JVM 플래그·자체 왕복 불가를 확인했다. 전부 반영했다.

인증 흐름

[1] 가입 화면 → window.open('/nice-auth')
[2] 팝업 → POST /api/auth/nice/request            same-site, 세션 O
      REQ_SEQ 발급(saveIfAbsent, 충돌 시 최대 5회 재발급) → 평문 조립 → 암호화
[3] 팝업 → NICE 표준창으로 폼 POST                 사용자 브라우저 → NICE
[4] NICE 자동 submit → POST /api/auth/nice/callback   cross-site, 세션 X, form-urlencoded
      복호화 → REQ_SEQ 대조 → compareAndSet(PENDING→VERIFIED) → resultToken 발급
      303 → /nice-auth/result?token=...           (실패 시 토큰 없이 303)
[5] 팝업 → POST /api/auth/nice/result { token }      same-site, 세션 O
      takeByResultToken → 세션 대조 → 세션에 CI 저장 → 이름·휴대폰만 반환
[6] 팝업 → window.opener.postMessage(...) → close   origin 검증
[7] 가입 제출 → 서버가 세션의 CI 사용 → 소비 후 제거

콜백에 세션 쿠키가 없는 것이 설계를 결정한 제약이다. SameSite=None으로 푸는 대신 콜백이 세션에 의존하지 않게 했다.

상태 전이 — NiceVerificationRecord

PENDING→성공 콜백 · CAS→VERIFIED→토큰 교환 · 원자적 꺼냄→세션 NICE_VERIFIED
PENDING→실패 콜백 · CAS→FAIL→교환 시 거부 · 제거

모든 전이는 ConcurrentHashMap의 원자 연산으로 한다. find→검사→save로 하면 같은 콜백 두 건이 동시에 둘 다 통과한다(리뷰에서 재현).

핵심 보안 속성

속성보장 방식상태
CI는 브라우저로 내려가지 않는다결과 응답·postMessage에 CI 없음, 서버 세션에만 저장. 통합 테스트가 응답 본문 전체를 훑어 확인지켜짐
가입은 서버 세션 값만 쓴다요청 DTO에서 3필드 제거. 인증 결과는 소비 후 제거(1회용)지켜짐
REQ_SEQ 1회용compareAndSet. 만료 검사 + 암호문 생성 시각 2차 게이트(Asia/Seoul)지켜짐
resultToken 1회용 + 세션 결속takeByResultToken(remove(key, value)) — 거부돼도 소각지켜짐
운영에 Mock 혼입 불가2×2 가드 + 실연동 설정 4개 필수. mock-enabled 기본 false — 설정 누락 시 기동 실패지켜짐
용도 대조requireFresh가 SIGNUP 대조지켜짐
원인을 사용자에게 구분해 보여주지 않는다파이프라인 실패 문구 1개, 원인은 로그로만. NICE 원시 오류코드 비노출지켜짐

벤더 모듈 실측 발견

libs/NiceID.jar(NiceID.Check.CPClient 단독, 2013년 빌드)를 javap와 직접 실행으로 확인했다. 설계 초안의 가정 다섯 개가 틀렸다.

항목설계 초안실측영향
Java 17 동작그대로 동작--add-exports java.base/com.sun.crypto.provider=ALL-UNNAMED 필수 — 생성자가 JDK 내부 클래스를 직접 만들어 IllegalAccessError. 레거시 기동 스크립트도 같은 플래그 사용(확인)build.gradle test·bootRun에 추가. 운영 스크립트 필요
자체 암호문 왕복가능 — 가짜 NICE 응답으로 테스트불가 — fnEncode 뒤 fnDecode는 항상 -6. 요청·응답 포맷이 다르다복호화는 배포 후 실인증으로만 검증
평문 길이 문자셋UTF-8EUC-KR — 모듈이 "euc-kr" 하드코딩(5곳)코덱 교체
getCipherDateTime암호문 인자인자 없음 — fnDecode가 채운 인스턴스 상태NiceDecodeResult로 평문·시각을 함께 반환
fnParse그대로 위임파싱 실패 시 입력 조각을 stdout에 직접 출력, 쓰레기 입력엔 예외 없이 null운영 파서를 우리 코덱으로 교체(사용자 결정)

최종 리뷰 결함 조치

구현 완료 시점 테스트 106개가 전부 순차 시나리오라 초록이었다. 최종 리뷰가 재현 테스트로 결함을 찾았다.

심각도결함조치
ImportantREQ_SEQ 충돌 — 모듈 값이 밀리초+random%100. 순차 2,000회 중 1,765건 중복, save가 앞사람 요청을 덮어씀saveIfAbsent + 최대 5회 재발급
Important콜백 동시 재전송 — check-then-act 경쟁으로 둘 다 통과compareAndSet
Important같은 토큰 동시 교환이 둘 다 성공takeByResultToken
MinorNICE 원시 오류코드가 응답에 노출로그에만
Minor원인별 메시지가 응답으로 새어 나감(상태코드는 통일했는데)문구 통일, 원인은 로그
Minor시간대 systemDefault — 운영 JVM이 UTC면 전 인증 거부. KST 개발 PC에서는 숨는다Asia/Seoul 고정 (UTC JVM으로 재현)
Minor콜백 예외 시 팝업에 원시 JSON토큰 없이 303 → 결과 화면이 FAIL 전달
Minor가드가 site-code만 확인실연동 설정 4개 필수
자체 발견코덱이 UTF-8, 벤더 fnParse가 stdout에 입력 조각 출력EUC-KR 교체 + 운영 파서를 코덱으로

동시성 테스트는 Store를 상속해 읽기 메서드 안에 CyclicBarrier(2)를 넣어 경쟁을 결정적으로 재현한다. 수정 전 5개 전부 실패를 확인했고, 수정 후 5회 반복 모두 통과했다.

결정 로그

#결정근거
1콜백은 세션에 의존하지 않는다cross-site POST라 SameSite=Lax 쿠키가 안 온다. SameSite=None은 전역 CSRF 표면을 넓힌다
2백엔드는 HTML을 반환하지 않고 303으로 프론트 라우트에 넘긴다백엔드에 프론트 리소스 금지 규칙
3MockNiceClient를 jar와 분리(Base64)jar 확보 전 개발 가능, 이후 자체 왕복 불가가 확인돼 결정이 옳았다
4mock-enabled 기본 false기본 true면 운영이 설정을 빠뜨렸을 때 가짜 CI로 가입이 된다. AUDIT_ALLOW_FALLBACK_SECRET과 같은 선례
5검증 실패는 전부 400, 감사 로그 대신 log.warn원인 구분 금지 원칙. 가입 전 익명 흐름이라 ActivityLog에 귀속할 행위자가 없다
6시각 파싱 실패는 거부하지 않고 2차 게이트만 건너뛴다포맷을 실응답으로 확인할 수 없다. 주 방어선(Store 대조)은 그대로다
7운영 파서를 벤더 fnParse에서 우리 코덱으로벤더가 파싱 실패 시 이름·CI 조각을 stdout에 찍는다. 호환성은 교차 검증 테스트가 보장
8도메인 카드 분리auth-account가 40KB 상한 348바이트 앞까지 찼다
