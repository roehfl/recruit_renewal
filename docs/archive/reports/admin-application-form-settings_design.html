신영증권 채용 Renewal (recruit)

지원서 설정 관리자 화면 - 설계

설계 완료 구현 대기 작성일: 2026-09-02

요약

공고별 지원서 설정을 지원서 설정 대메뉴로 분리하고, 현황판과 공고별 설정 상세(탭) 두 화면으로 구성한다.

핵심은 백엔드가 강제하는 불변식 placedSections == enabledSections다. 이를 위반한 공고는 지원자 form-page 조회가 예외로 막히므로, 현황판이 이를 RELAYOUT_REQUIRED로 탐지하고 폼 구성 화면(A안)이 위반 상태를 만들 수 없게 막는다.

또한 applicationFormConfig를 공고 등록/수정 요청에서 제거하고 전용 엔드포인트로 분리해, 공고 수정 화면이 설정값을 덮어쓰는 사고를 구조적으로 차단한다.

구현은 3개 slice로 나눈다: 계약 분리(백엔드) → 현황판 → 설정 상세 탭.

정보 구조 (IA)

기존 관리자 사이드바는 2단계까지만 렌더링한다(AdminSidebar.vue는 group.children까지만 순회). 따라서 3단계 구조를 쓰지 않고, 지원서 설정을 대메뉴로 승격하여 2단계를 유지한다.

관리자 사이드바 (2단계 유지)
  ├── 공고 관리
  │     ├── 공고 목록          /admin/job-postings
  │     └── 공고 등록          /admin/job-postings/new
  │
  └── 지원서 설정                                   ← 신규 대메뉴
        ├── 지원서 설정 현황    /admin/application-forms
        └── 질문 템플릿 관리    /admin/question-templates   ← 전역 스코프, 위치만 이동

메뉴에 등록하지 않는 화면 (route meta activeMenuPath 로 활성 표시)
  └── 공고별 지원서 설정        /admin/application-forms/:jobPostingId
        ├── [지원서 양식]  탭
        └── [폼 구성]      탭
              (자기소개서 질문 탭은 이번 범위 제외)
  • 스코프 분리가 IA의 근거다. 지원서 양식·폼 구성·자기소개서 질문은 jobPostingId에 종속되고, 질문 템플릿만 전역(/admin/question-templates)이다. 전역 화면만 사이드바에 직접 두고, 공고 종속 화면은 상세 탭으로 묶는다.
  • 이름 충돌 회피. 관리자에는 이미 지원자가 제출한 실물을 보는 지원 현황 / 입사지원서 화면이 있다. 설정 화면은 "지원서 설정" 계열 이름을 써서 구분한다.
  • 탭 UI는 MenuManageView의 nav.site-tabs / button.site-tab(밑줄형 커스텀 탭, role="tablist") 패턴을 재사용한다. a-tabs를 새로 도입하지 않는다.

설계 배경

기존 GET /admin/job-postings는 필터 파라미터가 page/size뿐이고, 설정 관련 필드도 없다. 공고마다 레이아웃 API를 호출해 채우는 방식은 N+1인 데다, getLayout은 applicationFormConfig가 없으면 예외를 던지므로 목록 전체가 실패한다. 따라서 전용 요약 엔드포인트를 신설한다.

컬럼

컬럼필드설명
공고명title, postingType클릭 시 설정 상세로 이동
공고/접수 상태status, receptionStatus배지 2개
접수기간receptionStartDateTime ~ receptionEndDateTime
섹션sectionSummary.enabledCount, requiredCount"8개 (필수 3)" 형태로 한 칸에 합침

초안의 10컬럼에서 "사용/필수 섹션"을 한 칸으로, "편집 가능"을 설정 상태 배지로 합쳐 8컬럼으로 축소했다.

configState 판정

값조건의미
RELAYOUT_REQUIRED layoutStored && placedSections != enabledSections 지원자 form-page 조회가 실패하는 상태. 최우선 경고이며 기본 정렬 최상단
MISSING applicationFormConfig == null 게시 불가. 기존 데이터에만 존재할 수 있다
DEFAULT !layoutStored ApplicationFormLayoutDefaultFactory 결과로 동작 중. 정상 동작하지만 확정되지 않음

editable(접수 시작 전 && 미마감)은 configState와 직교하는 별도 필드로 내려, 화면에서 자물쇠 아이콘으로 덧붙인다.

집계 전략

공고별 질문 수 · 첨부 요구 수 · 레이아웃 페이지/항목은 group by 집계 쿼리로 한 번에 조회한 뒤 메모리에서 조인한다. 공고당 개별 조회(N+1)를 금지한다.

페이지 조회 1회         : job_posting (필터 + 페이징)
집계 쿼리 3회 (in 절)   : job_posting_question   group by job_posting_id
                          job_posting_attachment_requirement  group by job_posting_id
                          application_form_page(+item)        group by job_posting_id
메모리 조인 → configState 계산 → 응답

폼 구성 화면 — A안 (팔레트 + 페이지 캔버스)

좌측 팔레트에 미배치 섹션을 모아두고, 우측 페이지 카드로 드래그해 배치한다. 팔레트가 비어야 저장 버튼이 활성화되어, 서버 불변식이 화면상의 명확한 목표로 번역된다.

┌──────────────┬─────────────────────────────────────────┐
│ 미배치 섹션   │  [1] 기본 정보            ↑ ↓ ✕          │
│  · 포상       │       ⠿ 기본정보  (필수)                 │
│  · 공백기간   │       ⠿ 병역      (필수)                 │
│  남은 2개     │                                          │
│              │  [2] 학력 · 경력          ↑ ↓ ✕          │
│ 비활성 섹션   │       ⠿ 학력      (필수)                 │
│  · 첨부파일   │       ⠿ 경력      (선택)                 │
│   (미사용)    │                                          │
│              │  [3] 추가 기록            ↑ ↓ ✕          │
│              │       ⠿ 자격증 / 어학                     │
│              │       ┌ 여기에 끌어다 놓기 ┐              │
│              │  ＋ 페이지 추가                           │
└──────────────┴─────────────────────────────────────────┘
  • 팔레트 3구역: 미배치(점선 강조) / 배치 완료(숨김 또는 흐리게) / 비활성(회색 + "공고 수정 화면에서 변경" 안내)
  • 페이지 카드: 제목 인라인 편집(필수, 100자), 설명(500자), 순서 ↑ ↓, 삭제. 항목이 0개가 되는 삭제는 허용하되 저장 시 차단
  • 저장 payload 매핑: 카드 순서 → pageNo/sortOrder(0부터 재부여), 카드 내 칩 순서 → 항목 sortOrder
  • 진입 시 경고: RELAYOUT_REQUIRED 상태면 "새로 활성화된 섹션이 있어 재배치가 필요합니다" 배너를 띄우고, 해당 섹션을 팔레트 미배치로 표시한다
  • 읽기 전용: editable == false면 드래그·편집을 모두 잠그고 미리보기 중심으로 표시한다
  • 한글 라벨: 백엔드 sectionName은 영문("Basic Info", "Questions")이므로 프론트에 sectionType 기준 한글 매핑 상수를 둔다

접수 중 섹션을 끄면 이미 제출된 지원서와 어긋난다. 접수 중 섹션 변경은 실무에서 사용하지 않는 것으로 확인되어 레이아웃과 동일 규칙으로 좁혔다.

등록 시 기본 설정 생성

공고 등록 요청 → 서버가 기본 config 생성 → DEFAULT → 설정 화면에서 확정 → OK

applicationFormConfig를 null로 두지 않는 이유: config가 없으면 getLayout·saveLayout·getPreview가 requireFormConfig 예외를 던지고, 게시도 불가하며, 지원자 form-page 흐름도 막힌다. 기존 코드가 config 존재를 전제로 작성되어 있어 null을 정상 상태로 승격하려면 ApplicationFormPageService, ApplicationSectionAccessService, ApplicationSubmitValidator 등 여러 지점의 전제를 재작성해야 한다.

결정 로그

#결정근거
1 폼 구성 화면은 A안(팔레트 + 페이지 캔버스) 사용자 선택. 전체 구조 조망과 페이지 간 이동이 가장 직관적
2 지원서 설정을 대메뉴로 승격, 2단계 유지 AdminSidebar.vue가 group.children까지만 렌더링해 3단계를 지원하지 않는다
3 공고 종속 화면은 상세 탭, 전역 화면(질문 템플릿)만 사이드바 탭 3종은 jobPostingId 필수. 사이드바 직접 진입 시 "어느 공고?" 선택 단계가 매번 필요해진다
4 현황판 진입 화면을 공고 목록 재탕이 아닌 설정 상태 대시보드로 목록 중복을 피하고, RELAYOUT_REQUIRED 탐지라는 고유 가치를 부여
5 applicationFormConfig를 공고 등록/수정 요청에서 제거 공고 수정 화면이 낡은 값으로 설정을 덮어쓰는 사고를 구조적으로 차단. 병합 로직 중복도 제거
6 등록 시 config를 null이 아닌 서버 기본값으로 생성 기존 코드가 config 존재를 전제로 한다. 기본값의 단일 출처가 프론트에서 백엔드로 이동하는 부수 효과도 있다
7 양식 설정 편집을 접수 시작 전으로 제한 레이아웃과 규칙을 통일. 접수 중 섹션 변경은 실무 미사용이며 제출된 지원서와 어긋난다
8 탭 UI는 MenuManageView의 site-tabs 패턴 재사용 사용자 지정. 접근성 속성(role="tablist")까지 이미 갖춰져 있어 신규 컴포넌트 도입이 불필요
9 요약 집계는 group by + 메모리 조인 공고별 레이아웃 API 호출은 N+1이며, config가 없는 공고에서 예외로 목록 전체가 실패한다

미결 사항

#질문현재 입장
1 기존 DB에 application_form_config가 없는 공고가 있는가? 백필이 필요한가? 운영 확인 필요. 존재한다면 현황판에 MISSING으로 노출되며, 기본값 백필 스크립트로 정리한다
2 현황판에서 RELAYOUT_REQUIRED 공고를 일괄 정정하는 기능이 필요한가? 이번 범위 제외. 개별 진입으로 처리하고, 빈도가 높으면 후속 검토
3 레이아웃 저장에 동시편집 보호가 필요한가? 현재 API는 낙관적 잠금이 없다. 관리자 동시 편집 빈도가 낮다고 보고 이번 범위 제외
4 자기소개서 질문 관리 탭은 언제 붙이는가? 탭 자리만 확보하고 후속 slice로 미룬다. 백엔드 JobPostingQuestionController는 이미 구현되어 있다

다음 단계 권장

S1(양식 설정 분리)부터 착수한다. 백엔드 요청 DTO 축소와 신규 엔드포인트가 나머지 두 slice의 선행 조건이며, 기존 테스트 컴파일 에러가 함께 발생하므로 독립 slice로 처리하는 편이 안전하다.

검증은 변경 범위만 실행한다. 백엔드는 JobPosting·ApplicationForm 관련 패키지 테스트, 프론트는 npm run type-check를 기준으로 한다.

S1 완료 후 계약 문서의 해당 항목을 확정 상태로 갱신하고, S2·S3를 병행한다.
