메일·SMS 메시지 발송 - 설계

설계 승인 S4 변경 반영 작성일: 2026-09-19 · 갱신: 2026-09-19

요약

관리자가 지원자에게 메일·SMS를 보내는 기능을 설계했습니다. 메시지 종류 5개(결과 발표, 서류 마감 임박, 면접 일정·장소, 면접 공지, 직접 입력)를 고르면 대상자와 문구가 자동으로 채워집니다.

수신자별 실제 값으로 미리보기하고, 인사팀 담당자에게 테스트 발송한 뒤 실제 발송합니다. 문구는 관리자가 템플릿으로 관리하고, 발송은 서버에서 비동기로 처리하며 발송 이력을 남깁니다.

발송 솔루션 제약(호출 1회 = 내용 1개 + 수신자 최대 10명)에 맞춰, 내용이 같은 수신자만 10명씩 묶고 사람마다 내용이 다르면 1명당 1회 호출합니다.

S4 변경: 발송 솔루션은 호출 때 거래 ID만 주고 실제 결과는 나중에 메시지큐로 보냅니다. 수신자·채널은 접수 후 "결과 수신 중"(REQUESTED)이 되고, 거래 ID로 결과를 매칭해 성공·실패로 바꿉니다. 발송 상태·건수는 저장하지 않고 조회할 때 계산하며, 시간이 지나도 실패로 처리하지 않습니다.

구현은 S1 템플릿 → S2 대상자·작성 → S3 발송 → S4 결과 수신·이력·마무리 4개 slice입니다. S1~S3는 구현 완료(미커밋)입니다.

발송 흐름

실제 발송

(발송 확인)→ 검증·대상자 재조회·교집합→ SENDING 저장→ (커밋 후 비동기)→ 발송 단위별 게이트웨이 호출→ REQUESTED + 거래 ID→ (메시지큐 결과)→ SENT / FAILED

접수 자체가 실패하면(호출 예외·거절) 바로 FAILED. 치환은 발송 요청 시점에 하고 결과를 이벤트로 디스패처에 넘깁니다(DB에는 원문만).

발송 단위 (게이트웨이 트랜잭션)

  • 호출 1회 = 메시지 내용 1개 + 수신자 최대 10명.
  • 채널별로 치환 결과가 완전히 같은 수신자끼리 묶어 10명씩 나눔. #{이름} 등으로 사람마다 다르면 1명당 1회.
  • 접수 결과와 나중에 오는 발송 결과 모두 그 단위 수신자 전원에 적용. 발송 단위 1개 = DB 트랜잭션 1개.
  • 메일 단위를 모두 보낸 뒤 SMS. 최대 3,000명 × 2채널 = 6,000회 순차 호출.

발송 결과 수신 (S4 변경)

  • 결과는 거래 1건당 1개(거래 ID + 결과코드). 그 거래 수신자(최대 10명) 전원에 적용. 메일·SMS 같은 솔루션.
  • 솔루션은 늦더라도 결과를 반드시 1번 보냄(서버가 내려가 있어도 재연결 시 수신). ack 없음, 중복 없음. 반영은 REQUESTED인 행만 바꾸는 멱등 처리.
  • 발송 요청에 우리 키를 넣을 수 없어 거래 ID로만 매칭. 연락처는 AES 무작위 IV라 조회 키로 쓸 수 없음.
  • 거래 ID 저장 전에 결과가 먼저 오면 메모리 버퍼(DeliveryReportBuffer)에 보관 → 단위 기록 직후·1분마다 재시도 → 10분 뒤 경고 로그와 함께 폐기(서버 1대 운영).
  • 성공 판정은 설정 recruit.message.success-result-codes(기본 0000). 실패면 결과코드를 사유로 저장.
  • 실제 소켓 클라이언트는 범위 밖. 받은 메시지를 DeliveryReportHandler.handle에 넘기기만 하면 됨.
발송 상태(계산)조건화면
SENDINGPENDING 수신자 있음발송 중 (1시간 지나면 "발송 중단")
RESULT_PENDINGPENDING 없고 REQUESTED 있음결과 수신 중 (1시간 지나면 "결과 미수신")
COMPLETED둘 다 없음완료

1시간 지연 표시는 화면 표시만 바꿉니다. 실패로 처리하지 않고, 결과가 오면 정상 표시로 돌아갑니다.

테스트 발송

솔루션 호출은 동기. 미리보기 중인 지원자의 값으로 치환, 메일 제목·SMS 앞에 [테스트]. 담당자 최대 5명이 같은 내용을 받으므로 채널당 호출 1회. 응답은 접수 결과(REQUESTED·FAILED·SKIPPED)이고, 화면은 이력 상세를 3초 간격(최대 2분)으로 다시 읽어 결과를 갱신합니다.

게이트웨이: MailGateway·SmsGateway 인터페이스 + 목업(가짜 거래 ID로 접수 성공, 3초 뒤 가짜 결과, 연락처에 fail이면 실패 코드). 로그는 연락처 마스킹·본문 미기록. 실제 연동은 사내 스펙 확정 후 구현체만 추가.

결정 로그

#결정근거
1독립 발송 메뉴 + 메시지 중심 화면(작성 + 실제 수신 화면 미리보기)분할·위저드 안 모두 반려. 대상자는 드로어로 빼고 내용 확인에 집중
2템플릿 1개 = 메일 + SMS같은 안내를 메일은 자세히, 문자는 짧게 보내는 경우에 맞춤
3결과 발표는 결과 상태 필터 + 자유 템플릿중립·합격·불합격 안내를 관리자가 골라 씀
4마감 임박 대상은 미제출(DRAFT) 지원자만광고성 발송 동의 문제 회피
5발송 이력 포함, 예약·재발송·첨부 제외범위 최소화
6발송 연동은 인터페이스 + 목업사내 연동 스펙 미정
7발송은 비동기프론트 요청 타임아웃 10초, 대량 발송 시간
8발송 단위 = 내용 1개 + 최대 10명, 개인화 시 1명당 1회발송 솔루션 트랜잭션 제약(사용자 지정)
9최대 발송 인원 3,000명사용자 지정
10수신자 연락처 AES 암호화 + 파기 연동지원서 기본정보 연락처와 같은 보호 수준
11렌더링 규칙을 서버·프론트에 각각 구현즉시 미리보기 필요. 규칙이 단순해 중복 비용 작음, 같은 테스트 예시로 일치 보장
12치환을 발송 요청 시점에 하고 결과를 이벤트로 디스패처에 전달관리자가 확인한 값 그대로 발송, 디스패치 때 재검증으로 멈추지 않음(S3 계획 변경)
13채널 상태에 "결과 수신 중"(REQUESTED) 추가솔루션이 결과를 메시지큐로 나중에 보냄(S4 변경)
14거래 ID를 수신자 행에 채널별로 저장해 매칭(별도 단위 테이블 없음)요청에 우리 키를 넣을 수 없음, 결과는 거래 단위 1건
15발송 상태·건수는 저장하지 않고 조회 시 계산결과가 여러 스레드에서 나눠 들어와 저장 집계를 고치면 경합
16시간이 지나도 실패 처리 안 함, 1시간 뒤 화면만 "결과 미수신"발송은 반드시 나가고 결과도 반드시 옴(사용자 확인)
17먼저 온 결과는 메모리 버퍼에 10분 보관서버 1대 운영, 거래 ID 커밋 전 도착하는 짧은 경합만 대비
18화면에서 이메일·휴대폰을 가리지 않음, 마스킹은 로그만사용자 결정(2026-09-19)
