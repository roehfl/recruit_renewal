신영증권 채용 Renewal

개인정보 파기 화면 · 강제 파기 · 자동 파기 설계

설계 완료 사용자 승인 작성일: 2026-09-20

요약

보존·파기·감사 백엔드 API 13종은 이미 구현·검증이 끝났지만 화면이 없어 파기가 한 번도 실행되지 않는 상태다. 이 설계는 그 공백을 메운다.

세 덩어리다. ① 삭제 요청을 받아 지원자 1명의 개인정보를 즉시 지우는 강제 파기, ② 보존기간 5년이 지난 지원서를 매일 새벽 자동으로 지우는 스케줄러, ③ 이 둘을 다루는 관리자 화면 1개.

보존 기준은 개인정보 처리방침에 이미 적혀 있는 "인력풀 5년 보관 · 삭제 요청 시 지체없이 삭제"를 그대로 따른다. 기산점은 공고 마감일(CLOSED_AT)로 잡아 사람이 공고마다 종료일을 확정하는 절차를 없앤다.

구현은 3개 slice로 나눈다: 강제 파기 백엔드 → 자동 파기 백엔드 → 화면.

배경

현재 단건 execute는 실행 시 적격성을 재검증한다. 따라서 보존기간이 남아 있는 지원서는 RETENTION_NOT_DUE로 스킵되고 파기되지 않는다. 즉 "지금 지워 달라"는 요청을 처리할 경로가 없다. 도메인 카드도 forced purge를 미구현으로 기록해 두었다.

스케줄 실행도 없다. 보존기간이 지나도 아무도 파기하지 않는다. 이 둘이 이번 설계의 대상이다.

전역 정책 1건만 쓴다. 근거는 이 서비스의 개인정보 처리방침 본문이다.

항목값근거

HIRING_ENDED_AT을 쓰지 않는 이유 — 수동 확정이 한 번이라도 빠지면 그 공고의 지원서는 ANCHOR_NOT_FIXED로 영원히 파기되지 않는다. 5년 단위에서 "공고 마감"과 "채용 실질 종료"의 차이는 무시할 수 있다.

강제 파기 — 적격성 판정 축약

forced 경로는 기존 적격성 9단계 중 2개만 적용한다. 나머지는 모두 무시한다.

판정forced이유
ALREADY_PURGED적용두 번 지울 것이 없다
RETENTION_HOLD차단법적 보존 의무가 삭제 요구권보다 우선한다
POLICY_NOT_FOUND · POLICY_CONFLICT무시정책은 기간 계산용. 강제 파기는 기간을 보지 않는다
ANCHOR_NOT_FIXED · RETENTION_NOT_DUE무시기간 무관이 강제 파기의 정의다
APPLICATION_NOT_TERMINAL · INVALID_STAGE_CONFIGURATION무시진행 중 전형이 있어도 지운다(확인 모달이 경고)
판정 이후 처리(관계형 PII tombstone → 첨부 metadata → 바이너리 saga → ref-count 익명화)는 기존 경로와 완전히 같다. 파기 로직 자체는 건드리지 않고 판정 모드만 넘긴다.

강제 파기 흐름

지원자 검색 → 상세 · 판정 확인 → confirm 강제 파기 실행 → 지원서별 tombstone → 계정 익명화 → PURGE_FORCED 감사
규칙내용
단위지원자 1명 전체. 모든 지원서 + Applicant 계정을 한 PurgeBatch로 처리한다. 일부만 지우면 계정에 이름·연락처가 남아 "지체없이 삭제" 약속을 못 지킨다
계정익명화되면 loginId가 null이 되어 로그인 불가. 재지원은 신규 가입
지원 0건 계정대상에 포함. item 없이 purgePersonalData만 수행
보류 충돌active hold가 하나라도 있으면 400 거부 + 화면 버튼 비활성
진행 중 전형파기한다. 확인 모달이 "진행 중 N건이 함께 사라진다"를 빨간 배너로 경고
사유ForcedPurgeReason 선택형 3값만. 자유 텍스트를 받지 않는다

사유를 선택형으로 제한한 이유

ActivityLog와 파기 대장(PurgeBatch·PurgeJobItem)은 파기 대상이 아니다. 담당자가 메모에 "홍길동 요청"처럼 쓰면 그 이름은 영구히 남는다. 선택형 코드만 받으면 이 경로가 아예 사라진다. 상세 경위는 오프라인 접수 대장이 맡는다.

자동 파기 — 실행 게이트

cron은 매일 울리되, 실제 스캔은 관문 두 개를 통과해야 돌아간다.

매일 03:00 (retention.purge-cron)
  ├─ 자동 파기 OFF?              → SKIPPED_DISABLED 기록 후 종료
  ├─ 오늘 < 다음 파기 예정일?     → SKIPPED_NOT_DUE 기록 후 종료
  └─ dryRun("SYSTEM")
       ├─ ELIGIBLE 0건            → NO_TARGET 기록 후 종료
       └─ execute(confirm, sourceDryRunBatchId, "SYSTEM")
                                  → EXECUTED + batchId 기록
     예외 발생                     → ERROR 기록 후 삼킴(다음날 재시도)

게이트가 필요한 이유

게이트가 없으면 dry-run이 매일 밤 전 지원서를 findAll로 훑고 지원서 수만큼 purge_job_item 행을 쌓는다. 대상이 0건인 5년 동안에도 그렇다. 지원자 1만 명이면 연 360만 행이다. 게이트는 편의 기능이 아니라 이 누적을 막는 장치다.

다음 파기 예정일 계산

정의: 아직 파기되지 않은 지원서를 가진 마감된 공고 중 가장 이른 closedAt + 보존기간.

상황반환값
미파기 지원서를 가진 마감 공고가 있음min(closedAt) + retentionPeriodDays
마감된 공고가 없음(전부 진행 중)9999-12-31
마감 공고의 지원서가 모두 파기됨9999-12-31
전역 보존 정책이 없음9999-12-31 + 화면 정책 경고
계산값이 과거이거나 오늘게이트 통과 → 스캔 실행
이 값은 보존기간만 계산한 하한이다. 적격성 9단계(전형 종료 여부 등)를 반영하지 않으므로 그날 실제 파기 건수가 0일 수 있다. 화면 문구를 "이 날짜부터 파기 대상이 생길 수 있습니다"로 쓴다. 쿼리는 1건이며 인덱스로 커버된다.

자동 파기 설정 저장

단일 행 테이블 retention_schedule_setting(id 고정 1).

컬럼타입내용
idBIGINT PK항상 1
enabledBOOLEAN NOT NULL자동 파기 on/off
last_run_atDATETIME마지막 스케줄 기동 시각
last_run_resultVARCHAR(30)SKIPPED_DISABLED · SKIPPED_NOT_DUE · NO_TARGET · EXECUTED · ERROR
last_run_batch_idBIGINT실행했다면 그 execute batch id
updated_by · updated_at—토글한 사람과 시각

안전 기본값

행이 없으면 enabled=false로 간주한다. 모르고 켜져 있는 것보다 꺼져 있는 편이 낫다. 최초 토글 시 행을 만든다.

RetentionPolicy.enabled를 재사용하지 않는 이유

정책을 끄면 스케줄만 멈추는 게 아니라 적격성 판정이 POLICY_NOT_FOUND가 되어 강제 파기 화면의 판정 표시와 감사 사유까지 오염된다. 두 스위치는 의미가 다르다.

SYSTEM actor

현재 AuditRequestContextResolver.resolve(actor)는 actorId가 있으면 무조건 ActorType.EMPLOYEE로 기록한다. 스케줄러 실행이 임직원 행위로 남으면 감사 로그가 거짓이 된다.

  • 예약 상수 SYSTEM을 두고, 이 값이면 ActorType.SYSTEM으로 기록한다(enum에 이미 있는 미사용 슬롯).
  • 각 서비스의 requireActor는 빈 문자열만 거부하므로 "SYSTEM"은 그대로 통과한다. 수정 불필요.
  • 임직원 loginId는 LDAP 사번 체계라 SYSTEM과 충돌하지 않는다.

#결정근거
1보존기간 5년, 기산점 CLOSED_AT처리방침 본문이 5년을 명시. 마감일은 자동 기록되어 수동 확정 누락 위험이 없다
2강제 파기 단위는 지원자 1명 전체일부만 지우면 계정에 이름·연락처가 남아 "지체없이 삭제"를 못 지킨다

4진행 중 전형도 파기하되 경고삭제 요구권 우선. 담당자가 결과를 알고 누르게 한다
5사유는 선택형 코드만감사 로그·파기 대장은 파기 대상이 아니다. 자유 텍스트는 PII 영구 잔존 경로다

알려진 위험
