설계 완료 Phase 07e 후속 S1~S5 구현 완료 (2026-09-09) 작성일: 2026-09-09

요약

관리자 지원현황 화면에서 지원서 상세를 A4 PDF로 저장하고 출력한다. 단건과 일괄 모두 백엔드 openhtmltopdf 단일 경로로 처리하며, 브라우저 인쇄(window.print)와 헤드리스 Chromium은 채택하지 않는다.

Phase 07e에서 deferred 처리했던 세 항목 — batch/zip 다중 PDF, 학기별 성적 상세 표, 사진(attachment) binary embed — 을 이번 슬라이스에서 회수한다.

현행 표시 모델이 Field(label, value) 구조라 세로 2열밖에 렌더하지 못하므로, 열 헤더를 섹션 레벨로 분리해 가로 표를 렌더할 수 있도록 DTO를 재설계한다.

일괄 다운로드는 체크박스 선택 방식이며 최대 20건으로 제한한다. 상한의 주 근거는 서버 부하가 아니라 PII 반출 규모 통제다.

지원현황 목록 화면에는 핸들러가 없는 껍데기 버튼 4개가 이미 배치되어 있다. 이번 슬라이스에서 미리보기를 제거하고, PDF 인쇄와 엑셀 다운로드를 실제 기능에 연결한다. 인쇄는 껍데기 상태로 보존한다. 검색조건 표의 채용정보 / 인적사항 / 기타 그룹 헤더 열도 함께 제거한다.

엑셀 연결 과정에서 기존 export 엔드포인트가 화면 검색조건의 일부만 지원하는 결함을 발견했다. 목록 조회는 필터 17개인데 export는 3개뿐이라 그대로 연결하면 화면에 보이는 결과와 엑셀 내용이 어긋난다. export 필터 확장을 별도 slice로 포함한다.

구현은 백엔드 4개 + 프론트 1개, 총 5개 slice로 분할한다.

구현 결과는 admin-application-pdf-export_implementation.html 참조. 이 문서는 설계 시점의 판단 근거를 남긴 기록이다.

헤드리스 Chromium을 거부한 추가 근거

  • 자기 자신을 호출하는 재귀 부하 — 브라우저가 SPA를 띄우면 서버가 자기 API를 20건 × 8~10회 = 최대 200회 HTTP로 호출한다. 현행 방식은 서비스 레이어 인프로세스 호출에 read-only 트랜잭션 1개다. 성능 차이가 아니라 아키텍처 차이다.
  • 인증 설계를 새로 해야 한다 — 프론트가 쿠키 인증(withCredentials: true)이라 헤드리스 브라우저에 세션을 넘겨야 한다. 서비스 계정 로그인은 감사 추적이 끊기고, 요청자 쿠키 주입은 HttpOnly를 우회하며, 단기 렌더 토큰은 발급·검증·폐기 로직이 새로 필요하다.
  • "화면 수정하면 PDF도 자동"은 절반만 참 — page.pdf()는 인쇄 렌더 경로를 타므로 @media print CSS를 여전히 직접 관리해야 한다. 자동 동기화되는 것은 필드·구조뿐이고 A4 레이아웃은 아니다.
  • ADR 0001-application-pdf-openhtmltopdf-avoid-itext-agpl의 락인 결정을 유지한다.

사진 embed 정책

Phase 07e에서 "attachment binary embed은 설계 범위 밖"으로 제외했던 결정을 이번 슬라이스에서 뒤집는다. 근거는 면접관이 인쇄물만으로 지원자를 식별해야 한다는 실사용 요건이다.

항목내용
식별 규칙attachmentType == 'ETC' && sectionType == 'BASIC_INFO' 중 마지막 항목. 프론트 loadAttachmentFile()과 동일 규칙을 백엔드에서 재현
로드 경로기존 AttachmentStorageService.load(storagePath) 재사용
embed 방식base64 data URI 인라인. 렌더러가 외부 리소스 로드를 금지하고 있어 인라인이 유일한 경로
지원 포맷지원서 첨부 허용 확장자가 jpg, jpeg, png뿐이고 PDFBox가 둘 다 처리 가능 → 리스크 없음
용량 상한잠정 5MB. 초과 시 사진을 생략하고 계속 진행 (일괄 20건 메모리 방어)
사진 없을 때빈칸 + "사진 없음" 표기. 화면은 회사 로고를 fallback으로 쓰지만, 인쇄물에서 사진 자리에 로고가 박히면 오히려 혼란을 준다
실패 처리사진 로드 실패는 PDF 생성 전체를 실패시키지 않는다 (사진만 생략, 경고 로그)

PoC 선행 openhtmltopdf 1.0.10이 data: 스킴 이미지를 처리하는지 구현 전에 확인한다. 미지원 시 대안은 커스텀 FSUriResolver 등록이다.

일괄 상한 20건의 근거

0. 화면 단위와 일치

확정 근거

목록 조회 API가 한 번에 20건을 내려준다(adminApplicationApi.getApplications의 기본 size = 20). 화면은 그 20건을 pageSize: 10으로 두 페이지에 나눠 보여줄 뿐이다.

즉 운영자가 한 화면에서 선택할 수 있는 최대치가 20건이므로, 상한을 20으로 두면 "보이는 것 전부 선택"이 항상 성립한다.

1. PII 반출 규모 통제

주 근거

한 번에 수백 명 지원서 전문을 받아가는 경로를 열면 서버는 멀쩡해도 통제가 뚫린다. 상한은 부하 방어가 아니라 반출 규모 제한으로 둔다.

감사로그에 선택된 applicationIds 전체를 남겨야 상한이 의미를 갖는다.

2. 동기 응답 타임아웃

보조 근거

단건 0.3~1초 추정 기준 20건이면 6~20초. 프록시/게이트웨이 기본 타임아웃 60초 안에 여유 있게 들어온다.

구현 후 실측하여 상한을 재조정한다.

3. 메모리

보조 근거

List<byte[]>로 전량을 메모리에 들지 않는다. temp 디렉토리에 순차 렌더 후 zip 스트리밍으로 동시에 1건분만 유지한다.

폰트는 subset 임베드라 PDF당 수십~수백 KB 수준.

A4 레이아웃 규칙

@page { size: A4; margin: 18mm 14mm; }   /* 인쇄 가능 폭 182mm — 기존 설정 유지 */
table       { table-layout: fixed; }      /* 폭 초과 시 잘림 방지 */
.value      { word-break: break-all; }    /* 기존 */
.section    { page-break-inside: avoid; }
thead       { display: table-header-group; }  /* 페이지 넘어가도 열 헤더 반복 */
축보장 수준설명
가로 (폭) 1페이지 보장 서버에서 확정 렌더하므로 브라우저 종류·사용자 인쇄 배율 설정과 무관하다. 브라우저 인쇄 방식 대비 결정적 우위
세로 (페이지 수) 1페이지 불가 학력·경력·자기소개서 분량이 지원자마다 가변이다. 자기소개서만 5000자면 2~3장. 목표는 "가로 1페이지 + 세로 N페이지, 표 중간 잘림 없음"

table-layout: fixed가 없으면 긴 이메일·URL 같은 무공백 문자열 하나가 표를 밀어 폭을 초과시킨다. openhtmltopdf는 폭이 넘칠 때 축소하지 않고 잘라내므로 반드시 필요하다.

화면 일치 정책 — 픽셀이 아닌 구조

목표는 "운영자가 화면과 PDF를 나란히 놓고 같은 문서로 인식"하는 것이다. 픽셀 일치는 추구하지 않는다.

증상

운영자가 이름 홍길동으로 검색해 화면에 3명을 보고 있는 상태에서 엑셀 다운로드를 누르면, 공고 전체 지원자가 담긴 파일이 받아진다. 화면과 산출물이 어긋날 뿐 아니라, 의도한 것보다 훨씬 많은 PII가 반출된다.

AdminExportController의 클래스 주석은 "대응 list 엔드포인트와 동일한 필터를 쓰되 page/size는 무시하고 전체 행을 내보낸다"고 기술한다. 즉 설계 의도는 원래 동일 필터였고, 이후 목록 필터가 확장되는 동안 export가 따라가지 못한 것으로 보인다. 프론트가 이 버튼을 연결하지 않았던 탓에 지금까지 드러나지 않았다.

S5a — export 필터 확장

채택

  • exportApplications가 AdminApplicationSearchRequest를 받도록 변경
  • JobApplicationService.buildSearchCondition를 공유해 목록과 동일한 조건 객체를 생성
  • 검색조건 기반 export 조회를 repository에 추가 (목록 쿼리를 페이징 없이 재사용)
  • 기존 ExportRowLimitExceededException 행 수 상한 유지
  • 감사로그 filters에 적용된 조건 전체 기록

현재 export는 countExportApplications / findExportApplications라는 전용 쿼리 경로를 쓰고 목록은 AdminApplicationSearchCondition 경로를 쓴다. 두 경로가 분리되어 있는 것이 불일치의 근본 원인이므로 이 슬라이스에서 통합한다.

S5b — 현행 파라미터로만 연결

거부

  • 프론트 작업만으로 끝나 비용은 거의 없음
  • 대신 화면 결과와 엑셀 내용이 계속 어긋난다
  • 운영자가 필터가 적용됐다고 오인할 수 있어, 결함을 드러내는 대신 감춘다
  • PII 과다 반출이 상시화된다

#질문현재 입장
1 openhtmltopdf 1.0.10이 data: 스킴 이미지를 처리하는가? S2 착수 전 PoC로 확인. 미지원 시 커스텀 FSUriResolver를 등록해 data:만 허용
2 사진 용량 상한을 얼마로 할 것인가? 잠정 5MB. 실제 업로드 사진 분포를 확인해 조정
3 단건 렌더 실측 시간은? 0.3~1초 추정. S1 완료 후 실측하여 20건 상한을 재검토 (0.3초면 상향 여지, 1초에 가까우면 유지)
4 일괄 중 1건 렌더에 실패하면? 잠정 fail-fast — 전체 요청을 500으로 실패시킨다. 렌더를 스트리밍보다 먼저 끝내므로 가능. 부분 성공 요구가 나오면 zip에 실패 목록 파일을 포함하는 방식으로 전환
5 개별 파일명에 지원자 이름을 넣는 것이 PII 정책상 허용되는가? PDF 내부에 이미 이름·연락처가 있고 파일 자체가 통제된 다운로드 경로이므로 수용. 구현 시 파일명 sanitize(경로 구분자·제어문자 제거) 필수
6 일괄 다운로드에 별도 권한을 둘 것인가? 현재는 기존 admin 권한을 그대로 사용. AdminExportController.EXPORT_APPLICATION_PII 상수가 이미 "PII export admin 분리" 의도를 남겨두었으므로, role matrix 세분화 시 함께 적용
7 인쇄 버튼의 최종 용도는? 이번 범위에서는 껍데기로 보존한다(결정 18). 브라우저 인쇄 동선이 필요한지, 아니면 제거할지는 별도 판단
8 엑셀 export 확장 시 행 수 상한(ExportProperties.maxRows)을 조정하는가? 현행 값 유지. 필터가 넓어지면 오히려 결과 행이 줄어드는 방향이므로 상한을 건드릴 이유가 없다
9 목록이 21건째부터 조회되지 않는 문제는 어떻게 하는가? 기존 결함, 이번 범위 밖. 프론트가 getApplications를 page 없이 호출해 항상 첫 20건만 받아오고, 화면은 그것을 pageSize: 10으로 두 페이지에 나눠 보여준다. 서버 페이징이 연결되어 있지 않아 21건째부터는 화면에 나타나지 않는다. 별도 작업으로 분리하되, 고치면 일괄 상한 20건의 근거(화면 단위 일치)도 함께 재검토해야 한다
10 export 조회를 목록 쿼리로 통합할 때 성능 저하가 없는가? 목록 쿼리는 페이징(20건) 전제로 작성됐고 export는 전체 행을 훑는다. S5 구현 시 실행계획을 확인하고, 필요하면 export 전용 fetch 전략을 유지하되 조건 생성 로직만 공유하는 절충으로 후퇴한다

다음 단계 권장

  1. api-contract.md 🟡 초안 기재 — 일괄 엔드포인트의 요청/응답 스키마를 구현 전에 등록한다 (통합 하네스 §3-1).
  2. S1 착수 — 표시 모델 재설계와 템플릿 재작성. 이 슬라이스가 PDF 품질을 결정하므로 가장 중요하다.
  3. S2 착수 전 data URI PoC — 미결 1번을 먼저 해소한다.
  4. S3 완료 후 렌더 시간 실측 — 20건 상한의 적정성을 데이터로 재확인한다.
  5. S5는 독립 실행 가능 — 엑셀 export 필터 확장은 PDF 경로와 의존이 없다. PDF를 먼저 끝내고 싶으면 뒤로 미뤄도 무방하다.
  6. S4·S5 완료 시 계약 🟢 확정 — 실제 구현과 api-contract.md를 일치시킨다.

향후 Phase 후보

  • 지원자 본인 PDF 다운로드 (07e에서 deferred 유지)
  • PII export 권한 분리 (EXPORT_APPLICATION_PII role matrix 적용)
  • 영속 ActivityLog 이관 — 현재 감사는 SLF4J 로그 기반
  • 대량 일괄이 요구되면 비동기 배치 + 다운로드 링크 발급 방식 검토
  • 인쇄 버튼 용도 확정 또는 제거
  • 다른 export 엔드포인트(전형결과, 면접, 면접평가)도 같은 필터 불일치가 있는지 점검
