요약

기존에는 JobPosition.workLocation이 단일 자유텍스트라 "직무는 같고 근무지만 다른" 모집을 별도 모집분야 행으로 쪼개 등록해야 했다. 이 슬라이스는 근무지를 공통코드로 승격하고, 모집분야 1건이 후보 근무지 N건을 갖도록 구조를 바꿨다.

지원자는 공고 상세 화면에서 직무를 고르면 그 직무의 후보 근무지가 드롭다운에 동적으로 채워지고, 직무·근무지를 함께 선택해 지원을 시작한다. 지원서 작성 화면에서는 선택 결과를 읽기 전용으로 표시한다.

후보 근무지 개수 자체가 직무별 분기다(0=선택 없음, 1=고정, N=선택). 별도의 필수 여부 플래그를 두지 않아 상태가 두 곳으로 갈라지지 않는다.

마이그레이션은 신규 공고부터 적용하며, 신규 엔드포인트는 추가하지 않았다.

관계 구조

JobPosting
└── JobPosition (n)
    ├── positionName / jobGroup / jobTitle / employmentType
    └── workLocations (n)  ← @ElementCollection, code + name 스냅샷
                              ↑ 후보 제시
JobApplication
├── jobPosition (FK)
├── jobPositionNameSnapshot   (스냅샷)
├── workLocationCode          ← 후보 중 지원자가 고른 1건
└── workLocationNameSnapshot  (스냅샷)

CommonCode (groupCode = WORK_LOCATION)
└── 공고 저장 시점에만 조회하여 code 유효성 검증 + displayName 스냅샷 생성
  • 지원서는 근무지를 코드 + 표시명 스냅샷으로 함께 보관한다. 공통코드 라벨이 나중에 바뀌어도 지원 당시 표기가 보존된다.
  • 공고도 저장 시점 라벨을 굳혀 둔다. 공고는 시점 문서이며, 라벨 변경은 공고를 다시 저장할 때 반영된다.
  • 근무지 유효성은 항상 해당 모집분야의 후보 목록 기준으로 판단하며, 공통코드 전체 목록을 기준으로 삼지 않는다.

후보 개수 기반 분기

후보 수의미지원자 화면저장값
0개 근무지 선택 개념 없음 근무지 드롭다운 미표시 null
1개 근무지 고정(예: IT = 본사) 자동 선택 + 비활성 표시 해당 코드
N개 지원자 선택 드롭다운 활성 선택 코드

별도의 required 플래그를 두지 않는다. 후보 개수 하나가 필수 여부·표시 여부·검증 규칙을 모두 결정하므로 상태가 어긋날 여지가 없다.

선택 흐름

공고 상세 → 직무 선택 → 후보 근무지 채움 → 근무지 선택 → POST /applications
지원서 작성 → 헤더에 읽기 전용 표시 → 제출 → 근무지 유효성 재검증

후보 목록은 공고 상세 응답 한 번으로 모두 내려오므로, 직무를 바꿔도 추가 API 호출이 발생하지 않는다. 직무 변경 시 근무지 선택은 초기화되며 후보가 1개면 자동 선택된다.

결정 로그

#결정근거
1 근무지 선택을 지원서 작성 단계가 아니라 공고 상세에 둔다 직무와 근무지는 같은 층위의 "지원 대상" 결정이라 화면을 가를 이유가 없고, 기존 생성·수정 요청 확장만으로 끝나 신규 엔드포인트가 0개다
2 선택값은 JobApplication에 저장한다 jobPosition과 같은 층위이며, ApplicationBasicInfo(암호화 개인정보 테이블)나 신규 섹션에 두는 안보다 파급이 작다
3 후보 근무지에 code와 name을 함께 저장한다(비정규화) 응답 DTO의 from(entity) 정적 팩토리 규약을 유지할 수 있고 읽기 경로에 조회가 끼지 않는다. 공고는 시점 문서라 라벨 스냅샷이 의미상으로도 맞다
4 필수 여부 플래그를 두지 않고 후보 개수로 분기한다 플래그와 후보 목록이 어긋날 여지를 없앤다. "근무지 무관"이 필요하면 후보에 해당 코드를 하나 추가하면 되므로 스키마 변경이 불필요하다
5 요청 DTO에 축약 생성자를 유지한다 ApplicationCreateRequest(jobPostingId, jobPositionId) 형태를 남겨 근무지 후보가 없는 경로의 호출부를 그대로 유지한다. 기존 JobPositionRequest가 쓰던 관례와 동일하다
6 마이그레이션은 신규 공고부터 적용한다 기존 자유텍스트는 표기 흔들림이 있어 코드로 자동 매핑할 수 없고, 현재 데이터가 테스트 데이터뿐이다

미결 사항 · 주의

#항목현재 입장
1 구 컬럼 job_position.work_location 정리 스키마는 ddl-auto: update로 관리되어 컬럼이 자동 삭제되지 않는다. 코드에서 더 이상 참조하지 않으므로 방치해도 무해하며, 정리는 수동 DDL 1회로 처리한다
2 공통코드 WORK_LOCATION 그룹 등록 코드 데이터가 없으면 관리자 공고 폼의 근무지 선택지가 비어 후보를 등록할 수 없다. 공통코드 관리 화면에서 그룹과 코드를 먼저 등록해야 한다
3 공고 수정 시 모집분야 행 재생성 기존 replaceJobPositions는 모집분야 행을 지우고 다시 만든다. 이번 슬라이스에서 손대지 않은 기존 동작이며, 이미 지원서가 붙은 공고를 수정할 때의 영향은 별도 확인이 필요하다
4 공통코드 displayName 변경 반영 공고·지원서 모두 저장 시점 라벨을 스냅샷으로 보관한다. 라벨을 바꾸면 이후 저장분부터 반영되며, 기존 공고는 재저장 시 갱신된다

다음 단계 권장

  • 운영 준비: 공통코드 관리 화면에서 WORK_LOCATION 그룹과 근무지 코드를 등록하고, 테스트 공고를 하나 만들어 0개·1개·N개 세 분기를 화면에서 확인한다.
  • 정리 작업: 구 컬럼 job_position.work_location을 수동 DROP한다.
  • 후속 후보: 근무지 기준 지원자 집계(공고별 근무지 분포)를 관리자 대시보드에 추가할지 검토한다. 이제 코드 기준 집계가 가능해졌다.
  • 후속 후보: 지원현황 엑셀 export에 근무지 컬럼이 포함되어야 하는지 확인한다.
