S1~S4 구현 완료 API 계약 확정 작성일: 2026-09-04

요약

레거시의 서류검증·서류전형·1차면접·최종면접 서브메뉴 4개를 공고 선택 → 전형 단계 탭 단일 화면으로 재구성했습니다. 단계가 공고별 동적 목록(Stage)이라 고정 서브메뉴가 필요 없기 때문입니다.

판정 방식을 바꿨습니다. 레거시는 엑셀 왕복이 유일한 경로였고 업로드 전 검증이 없었습니다. 이제 화면에서 직접 판정하는 것이 기본이고, 엑셀은 대량·오프라인 검토용 보조 경로로 남되 업로드 전 변경 내역 미리보기를 거칩니다.

백엔드는 신규 엔티티·테이블 없이 3건을 확장했고, 구현 중 발견한 부분 판정 업로드 차단 결함을 함께 고쳤습니다. 프론트는 화면 하나와 모달 둘, 드로어 하나를 추가했습니다.

슬라이스 4개(S1 백엔드, S2 화면 본체, S3 엑셀·정정, S4 단계 설정)로 나눠 진행했고 모두 완료했습니다.

서류검증 기능 3종은 사용 여부가 확인되지 않았고, 사용 중이더라도 개선 요구를 다시 수집해야 한다는 판단으로 보류했습니다. 필요한 도메인 데이터(자기소개서 답변, 복무·재학 기간)는 이미 있어 검색 조건 추가만으로 구현할 수 있습니다.

핵심 설계 결정

결정근거
메뉴 1개 + 단계 스텝퍼 단계가 공고별 동적 목록이라 레거시가 메뉴를 나눈 이유(고정 단계 테이블)가 새 도메인에 없습니다. 단계는 3~4개가 현실적이라 상단 스텝퍼가 그리드 가로폭을 확보하면서 진행 흐름을 보여줍니다.
화면 직접 판정이 기본, 엑셀은 보조 백엔드에 일괄 판정과 업로드 미리보기 API가 이미 있었습니다. 엑셀만으로 판정하면 잘못된 파일이 그대로 반영됩니다.
판정을 모아 한 번에 저장 행별 즉시 저장보다 실수를 되돌리기 쉽고 요청 수가 적습니다. 저장 전 변경은 행 배경색과 건수로 드러냅니다.
단계 설정을 이 화면의 드로어에 배치 단계는 공고 발행 후에도 바뀌고(백엔드 가드가 허용), 시작·발표·마감 버튼과 같은 화면에 있어야 상태를 보며 조작할 수 있습니다. 공고 상세와 지원서 설정 현황판에는 진입 링크만 뒀습니다.
엑셀 템플릿 한글화 인사 담당자가 PASSED 대신 "합격"을 쓸 수 있어야 합니다. 헤더·값 라벨을 한글로 바꾸고 결과 열에 드롭다운을 넣었습니다.
결과 목록은 비페이징 유지 공고당 수천 건 규모라 필터·페이징·카운트를 화면에서 처리하면 충분합니다. 규모가 커지면 페이징 API로 전환합니다.

단계 상태 전이와 화면

READY → 전형 시작 → IN_PROGRESS → 결과 발표 → RESULT_ANNOUNCED → 단계 마감 → CLOSED

발표 이후에는 결과가 잠기고 사유를 남기는 정정만 가능합니다. 지원자에게는 RESULT_ANNOUNCED·CLOSED 단계의 최신 결과만 노출됩니다.

단계 상태배너활성 액션그리드
READY · 결과 0건준비 중대상자 불러오기빈 상태
READY · 결과 있음준비 완료 · 대상 n명다시 불러오기, 전형 시작읽기 전용
IN_PROGRESS진행 중 · 발표 예정일괄 적용, 변경사항 저장, 엑셀 업로드, 다시 불러오기, 결과 발표편집 가능
RESULT_ANNOUNCED발표 완료엑셀 다운로드, 행 정정, 단계 마감잠금 + 정정 열
CLOSED마감엑셀 다운로드, 행 정정잠금 + 정정 열

버튼 활성 조건은 백엔드 가드를 그대로 미러링합니다. 막힌 버튼에는 이유를 툴팁으로 알립니다. 그래도 서버가 거부하면 단계·결과를 재조회해 화면을 서버와 다시 맞춥니다.

백엔드 변경 (S1)

신규 엔티티·테이블 없이 기존 API를 확장했습니다.

변경내용계약
AdminStageResultResponse 그리드 열 추가 기존 필드 유지, 뒤에 6개 추가: decidedBy, workLocation, applicationType, finalEducationLevel, finalSchoolName, previousStageResultStatus. 학력과 직전 단계 결과는 신규 AdminStageResultEnricher가 단계 단위 배치로 채웁니다(N+1 없음). 🟢 확정
진행 중 단계 발표일시 수정 허용 READY는 전체 수정(기존), IN_PROGRESS는 resultAnnouncementDateTime만 변경 가능. 잠긴 4개 필드가 현재 값과 다르면 400. 발표일 연기가 실제 운영에서 흔하기 때문입니다. 🟢 확정
엑셀 업로드 템플릿 한글화 헤더 7열 한글화, 결과 값 한글 라벨, 읽기전용 4열 회색 음영, 헤더 틀고정, 결과 열 드롭다운(합격/불합격/보류/결시/철회). 파싱은 한글 라벨과 enum 이름을 모두 받습니다. 🟢 확정
부분 판정 업로드 허용 계획 밖 발견 기존 구현은 대기를 허용값 밖으로 보고 먼저 오류 처리해, 프리필된 대기 행을 손대지 않고 올려도 파일 전체가 거부됐습니다. 즉 전원 판정 전에는 업로드 자체가 불가능했습니다. 파일 값이 대기이고 DB도 대기면 미변경으로 분류하도록 검증 순서를 바꿨습니다. 🟢 확정

최종학력 판정은 지원현황 조회와 같은 규칙(최고 학력, 동률이면 id 큰 행)을 씁니다. 두 화면이 같은 지원자에게 다른 학교를 보여주면 안 되므로 양쪽에 동기화 주석을 남겼습니다.

역할 분담

지원현황 조회는 지원서 횡단 검색·열람·내려받기를 맡고, 전형결과 관리는 단계 단위 쓰기를 맡습니다. 검색 결과는 여러 단계가 섞여 있어 발표·업로드 가드가 맞지 않기 때문입니다.

안전장치

관리자가 실수로 데이터를 잃거나 잘못된 대상에 판정을 적용하지 않도록 넣은 장치입니다.

상황처리
저장하지 않은 판정을 두고 이탈 단계 전환 · 공고 전환 · 라우트 이탈 · 브라우저 닫기 · 엑셀 업로드 진입 · 드로어 열기 여섯 경로에서 확인을 받습니다.
다른 관리자가 먼저 수정 (409) 목록만 다시 읽고 입력값은 유지해 재검토 후 다시 저장하게 합니다.
필터로 가려진 행이 선택된 채 일괄 적용 배지 숫자와 적용 대상을 모두 "지금 보이는 선택 행"으로 통일했습니다. 선택 자체는 지우지 않아 필터를 되돌리면 살아납니다.
엑셀 업로드 오류 미리보기에서 변경·미변경·오류를 행별로 보여줍니다. 한 행이라도 오류면 전체가 반영되지 않습니다. 거부 시에도 응답에서 실패 행을 꺼내 사유를 표시합니다.
발표 후 결과 변경 사유를 필수로 받고 이력에 남깁니다. 이력은 바뀐 항목만 골라 보여줍니다 — 점수만 바뀐 정정을 "합격 → 합격"으로만 보여주면 무엇이 바뀌었는지 알 수 없기 때문입니다.
명령 실패 후 화면이 서버와 어긋남 가드 실패의 흔한 원인이 오래된 화면이라, 실패 시에도 단계·결과를 재조회해 스스로 맞춥니다.
최종 단계 미지정 개인정보 보관 최종 단계가 정확히 1개가 아니면 그 공고의 지원서가 파기 대상에서 영구 제외됩니다. 화면에 드러나지 않는 실패라 상시 배너와 저장 시 확인으로 막습니다.
조회 실패와 데이터 없음의 혼동 단계 목록·결과 목록·정정 이력 모두 실패와 미존재를 구분해 표시하고, 실패 쪽에는 재시도 경로를 둡니다.

구현 중 잡은 결함

계획 단계에서 드러나지 않았고 코드를 읽거나 리뷰하면서 발견한 것들입니다.

결함증상처리
부분 판정 업로드 차단 전원 판정 전에는 엑셀 업로드 자체가 불가능. 레거시 대비 기능 후퇴였습니다. 수정
지원분야 열이 빈칸 표 컴포넌트가 값을 찾을 경로도 직접 그리는 코드도 없어 아무것도 렌더하지 않았습니다. 수정
발표 가드 누락 대기 0건만 확인하고 결과 0건을 놓쳐, 배너가 "발표할 수 있습니다"라고 하는데 서버가 거부하는 상태가 가능했습니다. 수정
단계 저장이 백엔드 가드에 걸리는 경로 4건 순서 재부여·생성 순서·최종단계 이전·신규 행 누락으로 각각 400이 나는 조합이었습니다. 수정
오류 행에 "변경 없음" 표시 변경 내역이 비었는지로 판정하면 파싱 실패 행까지 문제 없는 행으로 읽혔습니다. 수정
엑셀 다운로드 타임아웃 서버가 파일을 다 만든 뒤 응답을 시작하는데 기본 10초를 써서 대상자가 많으면 끊겼습니다. 수정
대상자 있는 대기 단계 삭제 제약 위반으로 서버 오류. 프론트에서 막을 방법이 없어 백엔드 결정이 필요합니다. 분리
경력기술서 다운로드 오류 지원현황 조회에서 서버가 파일명 헤더를 주지 않으면 코드가 그대로 실패합니다. 이번 범위 밖입니다. 분리

알려진 한계

항목내용
마감 공고의 진행 중 단계 교착 공고 마감은 되돌릴 수 없는데 시작·발표·마감이 모두 게시 상태를 요구합니다. 판정은 되지만 결과를 공개할 방법이 없습니다. 화면은 이유를 정직하게 안내하는 선에서 멈췄고, 근본 해결은 백엔드 정책 결정이 필요합니다.
2단계 이후 대상자 필터 없음 대상자 초기화가 공고의 제출 완료 지원서 전부를 넣고 발표는 대기 0건을 요구합니다. 직전 단계 결과 열은 있지만 필터는 없어, 1단계 불합격자까지 전원 판정해야 합니다.
결과 목록 초기 로딩 단계 결과를 한 번에 받으므로 공고당 수만 건이면 무거워집니다. 그 시점에 페이징 API로 전환합니다.
결과 내려받기 열 구성 기존 12열 그대로라 이번에 늘어난 6개 필드가 시트에 나오지 않습니다. 업로드 소스로도 쓸 수 없습니다.
결과 상태 라벨 동기화 라벨을 내려주는 API가 없어 화면이 같은 표를 직접 갖습니다. 한쪽만 바꾸면 엑셀 드롭다운과 화면 배지가 갈라집니다. 계약 문서에 경고를 남겼습니다.
공고 목록 50건 제한 공고 셀렉트가 50건까지만 조회합니다. 지원현황 조회도 같은 한계라 두 화면이 함께 움직여야 합니다.

다음 단계 권장

  1. 메뉴 등록 — 관리자 메뉴 관리 화면에서 /admin/stage-results를 등록해야 사이드바에 뜹니다. 코드 변경이 아니라 운영 작업입니다. 등록 전에는 주소 직접 입력이나 공고 상세·지원서 설정 현황판 버튼으로만 도달합니다.
  2. 백엔드 결함 2건 처리 — 대상자 있는 대기 단계 삭제, 마감 공고의 단계 교착. 둘 다 정책 결정이 선행되어야 합니다.
  3. 실사용 확인 — 백엔드를 띄운 환경에서 공고 하나로 단계 생성부터 마감까지 한 바퀴 돌려보는 것을 권합니다. 이번 구현은 타입 검사와 빌드로만 검증했고 브라우저 실사용 확인은 하지 못했습니다.
  4. 서류검증 기능 재검토 — 보류한 자기소개서 키워드 검색과 단기전역·단기졸업 체크의 실제 사용 여부를 확인하고, 사용 중이면 개선 요구를 다시 수집합니다.
