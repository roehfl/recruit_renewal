구현 완료 미커밋 작성일: 2026-09-19

요약

발송 솔루션이 호출 때 거래 ID만 주고 실제 결과는 나중에 메시지큐로 보내는 구조에 맞춰, 수신자·채널 상태에 "결과 수신 중"(REQUESTED)을 두고 거래 ID로 결과를 매칭해 성공·실패로 바꾸도록 했습니다.

발송 상태(발송 중·결과 수신 중·완료)와 건수는 저장하지 않고 조회할 때 계산합니다. 1시간이 지나도 완료되지 않으면 화면에만 "결과 미수신"·"발송 중단"으로 표시하고 실패로 처리하지 않습니다.

발송 이력 화면·상세 드로어, 테스트 발송 결과 자동 갱신, 지원서 파기 연동을 붙였고, 커진 도메인 카드를 message·message-delivery로 나눴습니다. 배치별 리뷰와 S4 전체 최종 리뷰(판정: 병합 가능)를 거쳤습니다.

상태 전이

수신자 채널

PENDING→ 솔루션 접수(거래 ID)→ REQUESTED→ 메시지큐 결과(거래 ID + 결과코드)→ SENT / FAILED
PENDING→ 접수 실패·거래 ID 없음→ FAILED (GATEWAY_ERROR)

발송 1건 (계산값)

상태조건화면
SENDINGPENDING 수신자 있음발송 중 → 60분 뒤 "발송 중단"
RESULT_PENDINGPENDING 없고 REQUESTED 있음결과 수신 중 → 60분 뒤 "결과 미수신"
COMPLETED둘 다 없음완료

지연 표시는 화면만 바꾸고 DB 값은 그대로입니다. 결과가 오면 정상 표시로 돌아갑니다.

리뷰 반영 (결정 로그)

#결정근거
1결과 반영 전에 거래 ID 존재부터 확인update와 확인 사이에 접수가 커밋되면 결과가 반영 없이 버퍼에서 빠져 영구 유실(Important)
2MessageRecipient에 @DynamicUpdate + 회귀 테스트채널 간 덮어쓰기로 메일 결과가 사라지는 경쟁
3단위 기록이 실패해도 다음 단위 계속 처리결과 반영이 같은 행을 동시에 잠그게 되어 락 타임아웃이 발송 전체를 멈출 수 있음
4상세 드로어는 요청 실패 후에도 5초 폴링 유지일시 오류 한 번에 갱신이 영구히 멈추던 문제
5?sendId=를 watch로 처리, 드로어 닫으면 쿼리 제거이력 화면에 있는 상태에서 "이력 보기" 알림을 눌러도 열리도록
6테스트 결과 폴링의 늦은 응답은 조용히 버림화면 이탈·발송 후 엉뚱한 토스트·경고 방지
7SMS 제목 자르기를 코드포인트 기준으로이모지가 반쪽으로 잘리는 문제
8화면에서 이메일·휴대폰을 가리지 않음, 로그만 마스킹사용자 결정(2026-09-19)
9도메인 카드를 message(24.0KB)·message-delivery(23.8KB)로 분할39.8KB로 40KB 상한에 닿음(카드 규칙)

미결 사항

#질문현재 입장
1거래 ID가 메일·SMS 통틀어 유일하고 재사용되지 않는가?유일하다고 가정. 겹치거나 재사용되면 결과에 채널을 넣어 채널별로 반영하도록 바꿔야 함(설계서 17절 8번).
2솔루션의 성공 결과코드 목록과 코드별 설명은?우선 0000만 성공, 설정값으로 교체.
3거래 1건 안에 수신자별 ID·결과가 따로 있는가?우선 거래 단위 결과를 수신자 전원에 적용.
4운영 DDL, 초기 템플릿, 발신 정보 실제 값, 메뉴 등록S1부터 이어진 미결.

수용한 위험: 테스트 발송 중 먼저 온 결과를 반영하다 DB 오류가 나면 요청 트랜잭션이 롤백되어 500이 남(매우 드묾). 대량 발송이 60분을 넘으면 진행 중에도 잠시 "발송 중단"으로 보일 수 있음.
