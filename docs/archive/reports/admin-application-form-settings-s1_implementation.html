요약

지원서 양식(섹션 사용/필수) 설정을 공고 등록/수정 API에서 떼어내고, 전용 엔드포인트 POST /admin/job-postings/{jobPostingId}/application-form-config 를 신설했다.

공고 수정 요청에서는 필드를 완전히 제거해, 공고 수정 화면이 낡은 값으로 설정을 덮어쓰는 경로를 구조적으로 없앴다. 공고 등록 요청에서는 @NotNull 만 풀어 선택 필드로 완화했다.

병합·검증 로직을 JobPostingService 에서 ApplicationFormConfigService 로 이관했고, 양식 편집 가능 시점을 레이아웃과 동일하게 접수 시작 전 && 미마감으로 통일했다.

백엔드 관련 테스트 59건 전부 통과, 프론트 type-check 통과.

설계 대비 변경점

설계 단계에서는 등록·수정 양쪽에서 필드를 제거하기로 했으나, 구현 착수 시 영향 범위를 재측정해 등록은 선택 필드 완화로 조정했다.

항목설계구현근거
JobPostingCreateRequest 필드 제거 선택 필드로 완화 new JobPostingCreateRequest(...) 호출부가 74곳 / 테스트 56개 파일이다. 게다가 테스트 고정 시계가 접수 기간 중이라 신규 엔드포인트로는 config 를 설정할 수 없어 엔티티 직접 조작 헬퍼를 39곳에 끼워야 했다. 서버 기본값을 무엇으로 잡느냐에 따라 제출 검증 테스트의 의미까지 바뀌는 위험도 있었다.
JobPostingUpdateRequest 필드 제거 설계대로 제거 덮어쓰기 위험은 수정에만 존재하며, 호출부가 6곳이라 비용이 낮다
서버 기본값 미정 분리 이전 등록 화면 기본값과 동일 전 섹션 사용 / 학력·경력·병역만 필수 / 첨부 미사용. 동작 보존이 목적
컨트롤러 이름 AdminApplicationFormController AdminApplicationFormConfigController S2 요약 목록은 /admin/application-forms, 양식 저장은 /admin/job-postings/{id}/... 로 base path 가 달라 한 클래스에 담을 수 없다

등록 요청에 필드가 남지만, 프론트는 더 이상 보내지 않으므로 "프론트가 더미값을 만들어 보낸다"는 문제는 해소됐다.

신규 클래스

ApplicationFormConfigService

Service com.shinyoung.recruit.service

지원서 양식 설정의 단일 소유자. 생성·병합·검증·편집 시점 가드를 모두 담당한다.

메서드역할
createFrom(ApplicationFormConfigRequest) 공고 등록 시 설정 생성. 요청이 null 이면 기본 설정을 만든다. JobPostingService.create 가 호출한다
save(Long, ApplicationFormConfigRequest) 편집 가능 시점 검증 → 기존 설정과 병합 → ApplicationFormConfigResponse 반환
validateEditable(JobPosting) 마감이면 거부, 접수 시작 시각 이후면 거부. ApplicationFormLayoutService 와 동일 규칙
merge(...), resolveUpdatedRequired(...) require* 생략 시 기존값 유지. 단 섹션을 끄면 필수도 함께 해제
defaultConfig() 전 섹션 사용 / 학력·경력·병역 필수 / 첨부 미사용

예외는 기존 관례대로 InvalidJobPostingException(400) 과 JobPostingNotFoundException(404) 을 쓴다.

알려진 한계

#항목현재 상태
1 양식 설정을 편집할 화면이 없다 등록 화면에서 카드를 제거했고 S3 [지원서 양식] 탭은 아직 없다. 신규 공고는 서버 기본값으로 생성되고 기존 공고 설정은 그대로 유지되므로 동작상 문제는 없으나, S3 전까지 관리자가 양식을 바꿀 경로가 없다
2 등록 요청에 필드가 남아 있다 선택 필드로 남겨 두었다. 프론트는 보내지 않으며, 향후 테스트 정리와 함께 완전 제거를 검토할 수 있다
3 기존 공고의 설정 누락 여부 미확인 application_form_config 가 없는 공고가 있으면 S2 현황판에 MISSING 으로 노출된다. 운영 데이터 확인 필요
4 접수 중 양식 변경 불가로 좁혔다 이전에는 공고 수정 API로 접수 중에도 변경할 수 있었다. 실무 미사용으로 확인된 동작이나, 긴급 정정이 필요한 상황에서는 제약이 된다

다음 단계 권장

S3(설정 상세 탭)를 S2보다 먼저 착수하는 것을 권한다. 한계 1번 때문이다. 양식 편집 경로가 없는 상태를 오래 두는 것보다, [지원서 양식] 탭을 먼저 붙여 기능 공백을 닫는 편이 안전하다.

S2(설정 현황판)는 신규 요약 API와 집계 쿼리가 필요해 독립적으로 진행할 수 있으며, S3와 병행 가능하다.

S3 착수 시 adminApplicationFormApi 모듈을 신설하고 양식 저장·레이아웃 조회/저장/미리보기를 한곳에 모은다. 레이아웃 화면은 A안(팔레트 + 페이지 캔버스)으로 구현한다.
