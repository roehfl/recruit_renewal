NICE 본인확인 기반 아이디(이메일) 찾기 — 구현

구현 완료 개발 서버 실인증 확인 완료 작성일: 2026-09-22 (같은 날 갱신)

요약

아이디 찾기 화면을 목업(하드코딩 결과)에서 NICE 실연동 본인확인 + 서버 조회로 바꿨다. 결과는 부분 마스킹한 아이디만 보여준다.

가입과 같은 2단계 흐름이다. 팝업이 용도 FIND_EMAIL로 요청을 발급받고, 인증 결과가 서버 세션에 담기면 새 API find-email이 이를 1회 소비해 식별 키(이름+생년월일+성별 HMAC)로 계정을 찾는다.

용도 대조를 양방향으로 막았다. 가입용 인증으로는 아이디를 찾을 수 없고, 아이디 찾기용 인증으로는 가입할 수 없다.

이후 아이디/비밀번호 찾기 화면을 가운데 단일 카드 + 탭 2개 구성으로 개편했다. 개발 서버에서 실인증 3건(가입 계정 조회·미가입 명의 안내·가입 회귀)을 사용자가 확인했다.

불변식

  • 인증 1회 = 조회 1회. 세션 인증 결과는 조회 전에 제거한다. 계정이 없어도 소비된다.
  • 용도 대조 양방향. requireFresh가 가입·아이디 찾기 양쪽에서 용도를 확인한다.
  • 원문 비노출. 응답은 마스킹 아이디뿐이다. 원문 아이디·생년월일·성별은 응답·로그에 없다.
  • 용도 기본값 없음. 호출부가 용도를 빠뜨리면 조용히 가입용이 되지 않고 400이 난다.

배포 이슈 해소

  • 증상: 팝업에 Invalid request.(응답 data: null).
  • 근거: request 요청 헤더가 Content-Length: 0, Content-Type 없음 — 본문 없이 전송. 현재 코드는 항상 {"purpose":"FIND_EMAIL"}을 보낸다(빈 값이어도 {}).
  • 원인: 새 AccountRecovery.vue(?purpose=FIND_EMAIL로 팝업 열기)는 반입됐지만 NiceAuthPopup.vue·niceApi.ts는 구버전이라 본문 없이 호출 → 새 백엔드가 본문 필수라 HttpMessageNotReadableException → 400.
  • 조치: 변경 파일 전체(프론트 수정 8·삭제 2, 백엔드 수정 3·추가 4) 반입 후 정상 동작. 코드 수정 없음.
  • 참고: 이 400 핸들러는 로그를 남기지 않아 서버 로그로는 원인을 알 수 없었다(원인 로그 추가는 제안만, 미적용).
