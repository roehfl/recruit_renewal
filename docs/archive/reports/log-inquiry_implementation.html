로그 조회 화면 — 설계·구현 완료

구현 완료 프론트 전용 화면 수동 확인 대기 작성일: 2026-09-20

요약

관리자 콘솔에 로그 조회 화면(/admin/logs)을 추가했다. 탭 2개로 지원자 브라우저 오류(ClientEventLog)와 관리자·시스템 서버 행위 증적(ActivityLog)을 조회한다.

두 조회 API는 이미 있던 것이라 백엔드 변경은 0건이다. 계약 변경도 없다.

주 용도는 CS·사고 추적이다. 두 로그 모두 지원자 이름·연락처를 저장하지 않으므로, 이름·휴대폰으로 지원번호를 찾아 주는 지원자 찾기를 지원자 이벤트 탭 안에 두었다.

구현은 12개 태스크로 나눠 진행했고 커밋 12건(2f190b4~4295e81)으로 끝냈다.

감사 로그는 관리자·시스템의 행위 증적이라 지원자 스코프가 아니다. 지원자 찾기와 조회 대상 배너는 지원자 이벤트 탭 안에만 있고, 감사 탭은 지원번호를 필터 입력칸으로 직접 받는다.

두 탭 모두 진입 시 자동 조회하지 않는다. 탭 버튼에 건수 배지를 두지 않고 목록 헤더의 총 N건 한 곳에서만 건수를 보여 준다.

검증 및 비즈니스 규칙

기간 상한

두 백엔드 서비스(AuditActivityReadService·ClientEventLogReadService)는 Duration.between(from, to)이 90일을 넘으면 400을 낸다. 날짜 개수가 아니라 Duration 판정이다.

화면은 날짜만 고르고 시작일T00:00:00 ~ 종료일T23:59:59를 보내므로, 시작일·종료일 차이가 89일까지만 통과한다. 그래서 표기·프리셋·검증을 모두 "시작일·종료일 포함 일수" 기준으로 맞췄다.

프리셋시작일차이비고
1일종료일0일당일만
7일종료일 − 6일6일지원자 이벤트 기본값
30일종료일 − 29일29일감사 로그 기본값
90일종료일 − 89일89일상한

조회 전에 rangeError로 먼저 막는다. 서버 400을 그대로 띄우지 않는다.

세션 단위 조회

이벤트 상세 → 같은 세션 이벤트 모두 보기 → 조회 대상 해제 → clientSessionId 로만 조회

조회 대상(지원번호)을 일부러 푼다. 한 세션에는 지원서 필드가 빈 행(전역 JS 오류·네트워크 오류 등)도 섞여 있어, 지원번호를 함께 걸면 그 행들이 빠지기 때문이다.

a-tab-pane은 처음 활성화되기 전까지 렌더링하지 않으므로(lazy), 탭을 바꾼 뒤 nextTick으로 패널 마운트를 기다린 다음 노출 메서드를 부른다.

결정 로그

#결정근거
1한 화면 안에 탭 2개로 둔다사용자·권한이 같고, 사고 조사 때 두 로그를 오간다. 사이드바 항목도 1개로 끝난다.
2지원자 찾기를 지원자 이벤트 탭 안에만 둔다감사 로그는 관리자·시스템 행위 증적이라 지원자 스코프가 아니다.
3이름·휴대폰 검색은 기존 GET /admin/applications로 푼다백엔드 신규 0건. 두 로그 테이블에 이름·휴대폰이 없어 지원번호 변환 단계만 있으면 된다.
4지원자 찾기 결과에 휴대폰 컬럼을 두지 않는다AdminApplicationSummaryResponse에 휴대폰 필드가 없다(검색 조건으로만 쓰인다). 동명이인은 생년월일로 가린다.
5지원번호 직접 입력칸을 항상 노출한다파기된 지원자는 이름 스냅샷이 익명화돼 검색되지 않는다. 이 경로만 남는다.
6감사 검색에 correlationId 필터를 넣지 않는다백엔드 변경이 필요하다. 추적은 applicationId 축으로 대체한다.
7진입 시 자동 조회하지 않는다주 용도가 CS 추적이라 검색키를 먼저 받는 편이 맞다. 감사 탭도 조건을 지정한 뒤 조회한다.
8탭 버튼에 건수 배지를 두지 않는다두 탭 필터가 독립이라 반대쪽 건수는 지금 보는 조건과 무관하고, 목록 헤더에 총 N건이 이미 있다.
9기간을 "포함 일수" 기준으로 표기·계산한다백엔드가 Duration으로 판정해 23:59:59를 붙이면 차이 89일이 실질 상한이다.
10크로스 점프 도착 시 기간을 90일로 연다도착 탭의 기본 기간(7일·30일)에 걸려 빈 목록이 나오는 것을 막는다.
11cleanup 버튼을 만들지 않는다매일 04:00 스케줄러가 같은 일을 하고, 감사 로그도 남지 않는 파괴 동작이다.
12URL 쿼리는 진입 시 읽기만 한다다른 화면에서 넘어오는 입구만 있으면 된다. 필터 전체를 직렬화해 되쓰는 것은 얻는 것보다 비싸다.

#질문현재 입장
1ROLE_PRIVACY_ADMIN 전용 계정이 /admin에 못 들어오는 것을 고칠 것인가?미해결. ADMIN_ROLES는 로그인 직후 이동 분기와 공유하는 값이라 영향 범위가 넓다. 별도 결정 필요.
2지원현황 화면에 "로그 보기" 링크를 달 것인가?받는 쪽은 구현됐다. 링크를 거는 것은 admin-application 화면 변경이라 별도 슬라이스.
3client-event-log 카드가 32.1KB로 권장 30KB를 넘었다. 분리할 것인가?상한 40KB까지 여유가 있다. 더 쌓이면 하위 도메인 분리 검토.
4두 drawer를 defineModel로 맞출 것인가?동작 차이는 없다. 관례 정렬이 필요하면 별도 작업.

다음 단계 권장

  1. 화면 수동 확인 — 관리자 계정으로 로그인해 조회 전 상태, 기간 상한 경고, 지원자 찾기, 크로스 점프 양방향, 마스킹 표시, 탭 전환 후 상태 유지를 확인한다. 자동 테스트가 덮지 못하는 구간이다.
  2. 사이드바 메뉴 등록 — /admin/menus에서 ADMIN 사이트에 path=/admin/logs 소메뉴를 만든다. 운영 작업이며 코드로는 추가되지 않는다.
  3. 지원현황 → 로그 보기 링크 — 별도 슬라이스로 진행한다. 딥링크 규격은 이미 준비돼 있다.
  4. ROLE_PRIVACY_ADMIN 진입 문제 — 고칠지 말지 먼저 정한다. 고친다면 로그인 직후 이동 분기까지 함께 본다.
