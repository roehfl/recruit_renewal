Phase 03d-0: StageResult Domain Design

Stage와 JobApplication 사이의 전형 결과 record를 구현하기 전에 역할, 관계, 상태, API 후보, 보안/감사 TODO를 정리한 설계 보고서다.

Design Only

Phase Summary

Java 코드, Entity, Repository, Service, Controller, DTO, Test, DB schema, SecurityConfig는 변경하지 않는다.

Recommended

Model

StageResult는 Stage + JobApplication 기준의 N:M 연결 결과 record로 설계한다.

Next

Implementation

다음 구현 추천은 Phase 03d-1: StageResult Entity + initialize/list admin API다.

Current Context

  • Phase 02에서 Stage는 구현됐고, StageResult는 Application 도메인 부재로 보류됐다.
  • Phase 03a에서 JobApplication 루트가 구현됐다.
  • Phase 03c에서 상세 섹션과 질문/답변 영역이 구현됐다.
  • 이제 전형 단계별 지원자 결과를 Stage + JobApplication 기준으로 설계할 수 있다.

Recommended Domain Model

  • StageResult -> Stage: N:1 unidirectional
  • StageResult -> JobApplication: N:1 unidirectional
  • Stage와 JobApplication에는 result collection을 추가하지 않는다.
  • cascade/orphanRemoval은 사용하지 않는다.
  • unique(stage_id, job_application_id)를 권장한다.

Entity Fields

id, stage, jobApplication, resultStatus, score, comment, decidedAt, decidedBy, createdAt, updatedAt

초기 score는 nullable 수동 입력으로 두고, 평가 집계 연동은 후속 Phase로 분리한다.

State Policy

Stage.statusStageResult behavior
READYinitialize 가능. 결과 확정 수정은 제한 또는 준비 작업 후보.
IN_PROGRESSinitialize 및 결과 입력/수정 가능.
RESULT_ANNOUNCED조회 가능. 일반 수정 금지. correction command 후보.
CLOSED조회 가능. 수정 금지.

발표 전 지원자 노출은 차단하고, PENDING 결과가 남아 있으면 announce command를 제한하는 방향을 권장한다.

Creation Strategy

초기 구현은 명시적 initialize command 기반 일괄 생성을 추천한다.

  • POST /admin/stages/{stageId}/results/initialize
  • 해당 공고의 SUBMITTED 지원서 기준
  • 누락된 row만 PENDING으로 생성
  • DRAFT와 사전 철회된 WITHDRAWN은 제외

JobApplication Policy

  • DRAFT: 대상 제외
  • SUBMITTED: initialize 대상
  • WITHDRAWN before initialize: 제외
  • row 생성 후 철회: row 보존, 미발표/미결정이면 WITHDRAWN 전환 후보
