Recruit Backend Codex Report

Phase 03i-1 Attachment File Upload/Download Design

Design Completed

Generated on 2026-05-20. Documentation-only design phase for applicant/admin attachment upload and download policy.

Executive Summary

Phase 03i-1 defines how the project should move from attachment metadata rows to real multipart upload and controlled download.

The recommended upload path is a new single-file multipart command: POST /applications/{applicationId}/attachments/files.

Before upload ships, Phase 03i-2 must add physicalFileStatus and harden metadata replace so it cannot delete or update file-backed rows or trust client-supplied storage fields.

The recommended download paths are applicant-owned and admin-owned streaming endpoints, both hiding storage internals.

No Java source, tests, security configuration, build files, YAML, database schema, or existing API behavior changed in this phase.

Storage Structure

Phase 03i-2 should start with local filesystem storage behind an abstraction.

Assumption Local filesystem storage is for development, single-node deployment, or shared-volume deployment. Multi-node production needs NAS, S3/object storage, or another shared durable store; sticky session is not a file storage solution.

applications/{applicationId}/{yyyy}/{MM}/{dd}/{uuid}.{ext}
RuleDecision
Physical filenameGenerated UUID or ULID, never the original filename
Storage pathServer-generated relative key under configured root
Path traversal defenseNormalize root and final path; reject if final path escapes root
CompensationRegister transaction rollback cleanup after file save and use saveAndFlush(...) to surface DB failures before return when possible.
Future migrationIntroduce AttachmentStorageService and LocalAttachmentStorageService

Test Plan

Upload

  • Owner DRAFT upload success
  • SUBMITTED/WITHDRAWN upload failure
  • Other applicant hidden 404
  • Size/extension/content-type failure
  • Count and total-size limit failure
  • Generated storage path under root
  • Uploaded row has physicalFileStatus=STORED
  • sortOrder request rejected and response sortOrder server-assigned
  • DB failure and rollback cleanup attempt
  • Metadata replace preserves file-backed rows and replaces only METADATA_ONLY rows

Download

  • Applicant owner download success
  • Admin download success
  • Attachment/application mismatch 404
  • Korean filename header handling
  • Missing physical file controlled 404
  • Rows without physicalFileStatus=STORED are not downloadable

Regression

  • Existing metadata path/purpose preserved
  • Storage fields rejected as client input with 400
  • Forbidden storage fields are detected explicitly, not by global unknown-property failure
  • File-backed sort/order/type edits deferred to explicit endpoint
  • Admin metadata read unchanged
  • Dashboard/list/result APIs unaffected
  • Submit validator unchanged until later policy phase
