Documentation-only design for per-posting attachment requirements, dashboard readiness, and submit validation.

Policy Decision

CandidateDecisionReason
Global requireAttachmentRejectedCannot express which file is required.
attachmentType onlyRejectedCannot distinguish the same type across sections.
sectionType onlyRejectedCannot express multiple files in one section.
attachmentType + sectionTypeRecommendedMatches current upload metadata and avoids row-id dependency.
Add sectionRecordIdDeferredNeeds row-level evidence semantics and applicant row ids.

Domain Structure

JobPosting 1 --- N JobPostingAttachmentRequirement
JobApplication 1 --- N ApplicationAttachment

Requirement is policy.
Attachment is applicant evidence.
FieldRule
jobPostingRequired owner posting.
attachmentTypeRequired AttachmentType.
sectionTypeRequired ApplicationSectionType.
requiredSubmit-blocking when true.
minCountRequired rules need at least one matching stored file by default.
displayName, descriptionSafe user-facing policy text.

Matching Rule

Source of Truth 
attachment.jobApplication.id == application.id
attachment.attachmentType == requirement.attachmentType
attachment.sectionType == requirement.sectionType
attachment.physicalFileStatus == STORED
attachment.deletedAt == null

Rows in METADATA_ONLY, MISSING, or DELETED do not satisfy a required attachment. Orphan physical files also do not satisfy readiness because they have no active DB row.

Security And Exposure

Warning

Policy responses must not expose storage internals or applicant evidence internals.

  • Do not expose storedFileName, storagePath, storage root, absolute paths, physical status, delete actor, or deletion reason.
  • Admin APIs reuse existing /admin/** security.
  • Public endpoints expose only requirement policy, not applicant upload state.

Remaining Issues

  • Manual MariaDB DDL remains needed for persistent database deployment.
  • STORED rows with missing physical files are an operational risk; Phase 03i-5-2 may use DB status only, but storage health scan/repair should correct broken rows before production enforcement.
  • Published posting mutation and effective-date behavior are deferred.
  • Per-rule active/versioning, max count, conditional rules, row-level requirements, and template linkage are deferred.
  • Submitted application status impact after admin deletion remains a product/audit decision.
