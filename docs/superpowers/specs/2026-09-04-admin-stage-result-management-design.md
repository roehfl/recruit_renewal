# 관리자 전형결과 관리 화면 설계

- 작성일: 2026-09-04
- 대상: 관리자 화면 `/admin/stage-results` — 공고별 전형 단계 설정 · 단계별 결과 판정 · 발표 · 정정 · 엑셀 왕복
- 범위: **프론트 신규 화면 1개(+드로어/모달)** + **백엔드 소폭 확장 3건**(§5). 신규 엔티티·테이블 없음.
- 시안: `docs/design/전형결과 관리 관리자 시안.html` — **시안 A(상단 스텝퍼)** 채택.

## 1. 배경 및 현황

### 1.1 as-is (레거시)

- 서브메뉴 4개(서류검증 / 서류전형 / 1차면접 / 최종면접). 메뉴마다 공고·지원분야·근무지·전형결과 검색이 같은 패턴으로 반복.
- 판정은 **엑셀 다운로드 → 엑셀에서 합격/불합격 편집 → 업로드**로만 반영. 업로드 전 검증·미리보기 없음.
- 서류검증의 자소서 키워드 검색, 단기전역·단기졸업 체크는 **이번 범위에서 보류**(§9).

### 1.2 기존 백엔드 (변경 없이 그대로 사용)

단계(`Stage`)는 공고별 동적 목록이고 결과(`StageResult`)는 단계 × 지원서 1행이다. 레거시가 메뉴를 나눈 이유(고정 단계 테이블)가 새 도메인엔 없다.

| 엔드포인트 | 용도 | 가드 |
| --- | --- | --- |
| `GET /admin/job-postings/{id}/stages` | 단계 목록(`stageOrder` 순) | — |
| `POST …/stages`, `POST …/stages/{stageId}`, `POST …/stages/{stageId}/delete` | 단계 생성/수정/삭제 | 공고 CLOSED 불가. 수정·삭제는 단계 READY만(수정은 §5.2로 완화) |
| `POST …/stages/reorder` | 순서 일괄 변경 (`items[{stageId, stageOrder}]`) | 공고 CLOSED 불가 |
| `POST …/stages/{stageId}/start` | READY → IN_PROGRESS | 공고 PUBLISHED |
| `POST …/stages/{stageId}/announce` | IN_PROGRESS → RESULT_ANNOUNCED | 공고 PUBLISHED, 결과 행 누락·PENDING 0건 |
| `POST …/stages/{stageId}/close` | RESULT_ANNOUNCED → CLOSED | 공고 PUBLISHED |
| `GET /admin/stages/{stageId}/results` | 단계 결과 전체 목록(비페이징 List) | — |
| `POST …/results/initialize` | 제출 완료(SUBMITTED) 지원서를 PENDING 행으로 생성. 기존 행 유지, 신규만 추가(멱등) | 단계 READY 또는 IN_PROGRESS |
| `POST …/results/{resultId}` | 단건 판정 | 단계 IN_PROGRESS, `resultStatus != PENDING` |
| `POST …/results/bulk` | 일괄 판정 (`items[{stageResultId, resultStatus, score, comment}]`) | 위와 동일. `@Version` 충돌 시 409 |
| `POST …/results/{resultId}/correct` | 발표 후 정정(사유 필수) + 이력 append | 단계 RESULT_ANNOUNCED 또는 CLOSED |
| `GET …/results/{resultId}/histories` | 정정 이력 | — |
| `GET …/results/upload-template` | 현재 값 프리필된 xlsx (POI 동적 생성, 정적 템플릿 없음) | — |
| `POST …/results/upload/preview` | 행별 검증 + diff. 영속 없음 | — |
| `POST …/results/upload/commit` | 재검증 후 all-or-nothing 적용. 오류·STALE 1건이라도 있으면 0건 반영 | 단계 IN_PROGRESS |
| `GET …/results/export` | 결과 목록 xlsx 다운로드(읽기 전용, 업로드 소스 아님) | — |

- `StageStatus`: READY → IN_PROGRESS → RESULT_ANNOUNCED → CLOSED.
- `StageResultStatus`: PENDING / PASSED / FAILED / ABSENT / WITHDRAWN / HOLD.
- 지원자 결과 조회는 RESULT_ANNOUNCED·CLOSED 단계만 노출, 정정 이력·점수·코멘트 미노출(기존 정책, 변경 없음).

### 1.3 기존 프론트

- `ApplicationStatus.vue`(지원현황 조회)는 지원서 횡단 검색·열람만 담당. 단계·결과 쓰기 UI 없음.
- Stage 관리 UI 없음. 현재 단계는 API로만 만들 수 있다.

## 2. 결정사항

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 메뉴 구조 | 메뉴 1개 "전형결과 관리". 공고 셀렉트 → 단계 스텝퍼 | 단계가 공고별 동적 목록. 고정 서브메뉴 불필요 |
| 지원현황 조회와 역할 분담 | 지원현황 = 횡단 검색·열람·export. 전형결과 = 단계 단위 쓰기 | 검색 결과는 단계 혼재라 가드·발표·업로드가 안 맞음 |
| 판정 방식 | 화면 직접 판정이 기본, 엑셀 왕복은 보조 | 백엔드 bulk·preview API 활용. 엑셀은 대량·오프라인 검토용 |
| 판정 저장 단위 | 로컬 변경을 모아 "변경사항 저장" 1회(`bulk`) | 행별 즉시 저장보다 실수 취소 가능, 요청 수 적음 |
| 단계 내비게이션 | 시안 A 상단 스텝퍼 | 단계 3~4개가 현실적, 그리드 가로폭 확보, 진행 흐름 가시화 |
| 단계 설정 위치 | 이 화면의 드로어. 공고 상세·지원서 설정 현황판엔 링크만 | 단계는 발행 후에도 바뀜(백엔드 가드가 허용). 라이프사이클 버튼과 같은 화면 |
| 시작된 단계 수정 | **발표일시만** 수정 허용(백엔드 완화 §5.2) | 발표일 연기는 흔한 운영. 이름·유형·순서는 잠금 유지 |
| 결과 목록 조회 | 비페이징 List 유지. 필터·페이징·카운트 클라이언트 처리 | 공고당 수천 건 규모. 페이징 API는 필요 시 후속 |
| 엑셀 템플릿 | 헤더 한글화 + 결과값 한글 라벨 + 엑셀 드롭다운(DataValidation) | HR 사용자가 `PASSED` 대신 "합격"을 쓸 수 있어야 함 |
| 서류검증 기능 | 보류 | 사용 여부 미확인. 사용 중이어도 개선 요구 재수집 필요 |

## 3. 동작 모델

### 3.1 단계 상태 → 화면

| 단계 상태 | 배너 | 활성 액션 | 그리드 |
| --- | --- | --- | --- |
| READY, 결과 0건 | "준비 중 · 접수 마감 {일자}" | 대상자 초기화 | 빈 상태(§4.9) |
| READY, 결과 있음 | "준비 완료 · 대상 n명" | 대상자 다시 불러오기, 전형 시작 | 잠금(셀렉트 비활성) |
| IN_PROGRESS | "진행 중 · 발표 예정 {일시} · 대기 n건" | 일괄 적용, 변경사항 저장, 엑셀 템플릿↓, 엑셀 업로드↑, 대상자 다시 불러오기, 결과 발표(대기 0건일 때) | 편집 |
| RESULT_ANNOUNCED | "발표 완료 · {일시} · 정정만 가능" | 엑셀 다운로드(export), 행 정정, 단계 마감 | 잠금 + 행 "정정" 버튼 |
| CLOSED | "마감" | 엑셀 다운로드, 행 정정 | 잠금 + 행 "정정" 버튼 |

- 공고가 DRAFT면 시작/발표/마감 버튼 비활성 + 툴팁 "공고 발행 후 가능". 공고가 CLOSED면 단계 설정 드로어 전체 읽기 전용.
- 버튼 활성 조건은 백엔드 가드를 그대로 미러링한다. 그래도 서버가 거부하면(경합) 서버 메시지를 그대로 표시하고 단계·결과를 재조회한다.

### 3.2 데이터 로딩

1. 진입: 공고 목록(`adminJobPostingApi.getJobPostings`) → 기본 공고 = 쿼리 `jobPostingId` → 없으면 접수 중 첫 공고 → 없으면 첫 공고.
2. 공고 확정: 단계 목록 조회. 기본 단계 = 쿼리 `stageId` → 없으면 IN_PROGRESS 단계 → 없으면 첫 READY → 없으면 마지막 단계. 단계 0건이면 빈 상태.
3. 단계 확정: 결과 목록 조회(1회). 카운트 6종(대상/대기/합격/불합격/보류/결시)과 필터 옵션(지원분야·근무지 distinct)은 이 목록에서 파생.
4. 공고·단계 변경 시 라우터 쿼리를 `replace`로 동기화. 새로고침·링크 공유 시 같은 위치 복원.

### 3.3 판정 편집

- 상태: 서버 원본 `results[]` + 로컬 변경 맵 `dirty: Map<stageResultId, {resultStatus, score, comment}>`.
- 행 셀렉트/점수/코멘트 변경 → `dirty`에 기록. 원본과 같아지면 항목 제거. 변경 행은 배경색 + 판정일시 열에 "저장 전".
- 일괄 버튼(합격/불합격/보류/결시)은 **체크된 행에 로컬 적용만**. 철회(WITHDRAWN)는 일괄 버튼에 없고 행 셀렉트에서만 선택 가능. 대기(PENDING) 옵션은 **원본이 대기인 행에서만** 셀렉트에 남겨 둔다(되돌리기 용도). 대기로 되돌린 행은 원본과 같아지므로 `dirty`에서 빠지고 저장 대상이 아니다. 원본이 판정된 행은 대기로 바꿀 수 없다(백엔드 규칙).
- "변경사항 저장 (n)" → `bulk` 1회. 성공 시 응답 `results`로 해당 행 교체, `dirty` 비움. "변경 취소" → `dirty` 비움.
- 실패: 400은 메시지 표시(변경 유지). **409**는 "다른 관리자가 먼저 수정했습니다. 목록을 새로 불러왔습니다." + 목록 재조회, `dirty`는 유지해 사용자가 재검토 후 다시 저장.
- 미저장 변경이 있을 때 공고/단계 변경·라우트 이탈·브라우저 닫기는 확인(`onBeforeRouteLeave`, `beforeunload`). 엑셀 업로드 진입도 차단("먼저 저장하거나 취소하세요").
- 클라이언트 검증: 점수 숫자, 코멘트 2000자.

### 3.4 초기화 · 시작 · 발표 · 마감 · 정정

- 대상자 초기화 / 다시 불러오기: 확인 모달("제출 완료 지원서를 대상자로 등록합니다. 기존 행은 유지됩니다.") → `initialize`. 응답 `createdCount/existingCount/skippedCount`를 토스트로 표시("신규 3 · 기존 125 · 제외 2").
- 전형 시작: 확인 모달 → `start`.
- 결과 발표: 대기 0건일 때만 활성. 확인 모달("대상 n명 중 합격 a · 불합격 b · … 결과가 지원자에게 공개됩니다.") → `announce`. 미저장 변경 있으면 먼저 저장 유도.
- 단계 마감: 확인 모달 → `close`.
- 정정(발표·마감 후): 행 "정정" → 모달(현재 결과·점수·코멘트 표시, 변경할 결과·점수·코멘트·**사유 필수**) → `correct`. 성공 시 행 교체. 모달을 열 때 `histories`를 조회해 모달 안에 이력 표를 표시한다(그리드에는 정정 횟수를 표시하지 않는다 — 행마다 이력 조회가 필요해서 제외).

### 3.5 엑셀 왕복

1. 템플릿↓: `upload-template`을 blob으로 받아 저장(지원현황 조회의 경력기술서 다운로드 방식 재사용).
2. 업로드↑: 파일 선택 즉시 `preview`. 미리보기 모달(§4.7). `.xlsx`만 `accept`.
3. 적용: `committable`(오류 0건)일 때만 활성. 같은 파일을 `commit`. `APPLIED` → 모달 닫고 결과 재조회 + 토스트("41건 반영"). `REJECTED_VALIDATION`(400)·`REJECTED_STALE`(409)·낙관적 잠금 409 → 모달 유지, `failedRows`만 표로 표시 + 안내("파일을 수정한 뒤 다시 업로드하세요").
4. 발표 후 "엑셀 다운로드"는 `results/export`(읽기 전용 목록). 업로드 소스가 아니므로 모달에서 업로드하면 헤더 불일치로 거부된다 → 안내 문구에 "템플릿 다운로드 파일만 업로드 가능" 명시.

### 3.6 단계 설정

- 드로어 열기: 스텝퍼 ⚙, 빈 상태 버튼, 공고 상세/지원서 설정 현황판 링크.
- 행 = 단계. 편집 가능 범위:

| 단계 상태 | 이름·유형·최종단계 | 발표일시 | 순서 | 삭제 |
| --- | --- | --- | --- | --- |
| READY | O | O | O | O |
| IN_PROGRESS | X | **O** (§5.2) | X | X |
| RESULT_ANNOUNCED / CLOSED | X | X | X | X |

- 저장: 신규 행 → `create`, 변경 행 → `update`, 삭제 → `delete`, 순서 변경 → `reorder`(변경 시 1회). 최종 단계는 하나만(체크 시 다른 행 해제, 백엔드도 검증).
- `stageOrder`는 드로어가 **10 단위**로 부여한다(10, 20, 30…). 새 단계는 `max + 10`으로 맨 뒤에 붙는다.
- 순서 변경 규칙(백엔드 `reorder`는 "전 단계 포함 + 전 단계 READY"일 때만 허용):
  - 모든 단계가 READY → 드래그 허용. 저장 시 순서를 10 단위로 다시 매겨 `reorder` 1회.
  - 시작된 단계가 하나라도 있으면 드래그 비활성. 대신 READY 행에 **"맨 뒤로"** 버튼을 두고 `update`(`stageOrder = max + 10`)로 처리한다. "1차 면접 진행 중에 2차 면접을 추가하고 최종 면접을 그 뒤로 보내기" 시나리오를 이걸로 커버한다. 그 외 위치 이동은 지원하지 않는다.
- 유형 옵션: 서류 / 1차 면접 / 2차 면접 / 최종 면접 / 기타 (`StageType`). 라벨은 기존 공통코드 `STAGE_TYPE` 재사용.

## 4. 화면 사양

### 4.1 헤더

- 제목 "전형결과 관리", 설명 "공고를 선택하고 단계별로 결과를 판정·발표합니다."
- 우측 공고 셀렉트(`a-select`, show-search). 라벨 = 공고명 + 접수 상태.

### 4.2 스텝퍼

- 단계별 칸: 번호(완료면 ✓), 단계명, 부제(상태 라벨 · 발표일 또는 대상 수). 선택 단계 강조. 우측 끝 ⚙ "단계 설정".
- 상태 라벨: READY "대기", IN_PROGRESS "진행중", RESULT_ANNOUNCED "발표완료", CLOSED "마감". 라벨은 프론트 상수 맵.
- 단계 6개 초과 시 가로 스크롤.

### 4.3 배너 · 카운트

- 배너 색: READY 파랑(info), IN_PROGRESS 노랑(warn), RESULT_ANNOUNCED 초록(ok), CLOSED 회색. 우측에 해당 상태의 라이프사이클 버튼.
- 카운트 카드 6개: 대상 전체 / 대기 / 합격 / 불합격 / 보류 / 결시. 카드 클릭 = 결과 필터 토글.

### 4.4 툴바

- 1열: 필터(지원분야 셀렉트, 근무지 셀렉트, 결과 셀렉트, 이름 입력) · 우측 엑셀 템플릿↓ / 엑셀 업로드↑ (IN_PROGRESS) 또는 엑셀 다운로드(발표 후).

## 5. API 계약 (변경분 — `api-contract.md`에 "전형결과 관리" 섹션으로 🟡 기재 후 구현 시 🟢)

### 5.1 `AdminStageResultResponse` 확장 (하위호환, 필드 추가만)

- 추가: `workLocation`(지원자가 선택한 근무지 표시명, 없으면 null), `applicationType`(`JobPositionApplicationType`), `finalEducationLevel`, `finalSchoolName`(최고 학력 행 기준 — 지원현황 조회와 동일 판정), `previousStageResultStatus`(같은 공고에서 `stageOrder`가 바로 앞인 단계의 결과, 없으면 null), `decidedBy`.
- 적용 엔드포인트: `GET /admin/stages/{stageId}/results`, `initialize`·`bulk`·단건·`correct` 응답 모두(같은 DTO).
- 구현(S1 확정): `workLocation`·`applicationType`·`decidedBy`는 이미 로드된 엔티티에서 바로 꺼낸다. 학력 2개와 직전 단계 결과만 신규 `AdminStageResultEnricher`가 단계 단위 배치로 채운다. N+1 없음.
- 최종학력 판정은 `JobApplicationService.loadAdminSummaryEnrichments`와 **같은 규칙(복제)**이다. 코드 재사용이 아니라 비교자를 복제했고, 양쪽에 "한쪽만 바꾸면 두 화면 값이 어긋난다"는 동기화 주석을 남겼다. 지원현황 조회와 그리드가 같은 지원자에게 다른 학교를 보여주면 안 된다.
- 관리자 전용 응답이므로 `decidedBy` 노출 가능(지원자 DTO는 변경 없음).
- `GET …/results/export`의 열 목록은 이번 범위가 아니라 그대로다. **늘어난 6개 필드는 export 시트에 나오지 않는다.**

### 5.2 단계 수정 완화

- `POST /admin/job-postings/{id}/stages/{stageId}` (`StageUpdateRequest` 형태 불변).
- READY: 기존과 동일(전체 수정).
- **IN_PROGRESS: `resultAnnouncementDateTime`만 변경 허용.** `stageName`·`stageType`·`stageOrder`·`finalStage`가 현재 값과 다르면 400. 값이 같으면 순서 중복·최종단계 유일성 재검증은 건너뛴다(바뀌지 않음이 보장되므로).
- `resultAnnouncementDateTime`에 null을 보내면 발표일시가 비워진다(미정으로 되돌리기).
- 400 메시지는 이 API의 기존 관례대로 **영문**이다: `In progress stage allows changing resultAnnouncementDateTime only.` 초안에 적었던 한글 문구는 채택하지 않았다(다른 `InvalidStageException` 메시지가 모두 영문). 사용자 문구는 프론트가 만든다.
- RESULT_ANNOUNCED·CLOSED: 기존과 동일(거부, `Only READY stage can be changed.`).

### 5.3 엑셀 템플릿 한글화 (`upload-template` 생성 + 파서 동시 변경)

헤더(파서 시그니처, 순서 고정):

| 시스템ID(수정금지) | 수험번호(수정금지) | 이름(수정금지) | 수정토큰(수정금지) | 결과 | 점수 | 코멘트 |
| --- | --- | --- | --- | --- | --- | --- |

- 수정금지 4열은 회색 채움. 열 숨김은 하지 않는다(사용자가 일부 열만 정렬해 행이 어긋나면 기존 3중 교차검증이 오류 행으로 잡는다). 헤더 행 고정(freeze).
- 결과 열 값: `대기`(PENDING, 프리필 전용) / `합격` / `불합격` / `보류` / `결시` / `철회`. 업로드 파싱은 **한글 라벨과 enum명 둘 다 허용**(trim, 대소문자 무시). 빈칸은 기존대로 오류("결과는 필수입니다").
- **부분 판정 업로드 허용(검증 순서 변경).** 변경 전 구현은 `대기`(PENDING)를 허용값 밖으로 보고 먼저 오류 처리하므로, 프리필된 대기 행을 손대지 않고 올려도 파일 전체가 거부됐다(= 전원 판정 전엔 업로드 불가). 변경 후: 파일 값이 `대기`이고 DB 현재 값도 PENDING이면 **미변경(UNCHANGED)** 으로 분류해 적용 대상에서 제외. 판정된 행을 `대기`로 되돌리면 오류, 대기인 채로 점수·코멘트만 입력해도 오류(bulk가 어차피 거부하는 조합을 먼저 막는다).
- 결과 열에 DataValidation 명시 목록 `[합격, 불합격, 보류, 결시, 철회]`. 적용 범위 2행 ~ (데이터 행 수 + 1), 데이터 0행이어도 2행에 건다. **빈칸도 허용하지 않고**(`setEmptyCellAllowed(false)`) `ErrorStyle.STOP`으로 막는다. `대기`는 프리필 전용이라 목록에 없다.
- 오류 메시지의 `resultStatus` 표기를 "결과"로 변경. 되돌리기 금지 문구에는 동시 편집 안내를 덧붙인다("판정된 결과를 대기로 되돌릴 수 없습니다. 다른 관리자가 이미 판정했다면 템플릿을 다시 받으세요.") — 다른 관리자가 먼저 판정하면 손대지 않은 대기 행이 이 오류를 내기 때문이다.
- 오류 문구에 사용자 입력을 되비출 때는 **50자까지만 싣고 `…`로 자른다**(셀 길이에 비례해 preview 응답이 커지지 않도록).
- 기존 영문 헤더 파일은 헤더 불일치로 거부된다(템플릿을 다시 받으면 되므로 호환 유지 안 함).

- 서류검증 보조 필터(자소서 키워드, 단기전역, 단기졸업). 사용 여부 확인 후 별도 설계. 도메인 데이터(`answerText`, 복무·재학 기간)는 이미 있어 검색 조건 추가만으로 가능함을 기록해 둔다.
- 결과 목록 페이징·서버 필터 API.
- 발표 시 이메일/SMS 알림, 면접 점수·평가 연동, 지원자 화면 변경.
- 지원현황 조회 화면의 기존 미구현 버튼(인쇄·PDF·엑셀).

## 10. 알려진 한계

- 결과 목록을 한 번에 받으므로 공고당 수만 건이면 초기 로딩이 무거워진다. 그 시점에 페이징 API로 전환.
- 낙관적 잠금은 행 단위다. 같은 단계를 두 관리자가 동시에 편집하면 409가 자주 날 수 있다. 화면에 "마지막 조회 {시각}"을 표시해 오래된 화면임을 알 수 있게 한다.
- 엑셀 미리보기는 STALE을 판정하지 않는다(백엔드 정책). 미리보기 통과 후 적용에서 거부될 수 있음을 푸터 문구로 안내한다.

## 11. S1 완료 후 프론트(S2~S4)가 알아야 할 것

S1 통합 리뷰에서 확인된 사실이다. 프론트 착수 전에 읽는다.

- **스텝퍼 부제의 "대상 수"는 현재 API로 못 만든다.** `StageListResponse`에 결과 건수가 없고, 결과 목록은 선택 단계 1개만 로드한다. 부제를 "상태 · 발표일"로 줄이거나 단계별 카운트 API를 따로 만든다. §4.2 시안은 대상 수를 전제하므로 이 결정이 필요하다.
- **§4.9의 "제출 완료 지원서 n건"은 가능하다.** `GET /admin/applications?jobPostingId={id}&status=SUBMITTED&size=1`의 `totalElements`를 쓴다.
- **진행 중 단계를 수정할 때 잠긴 4개 필드에 현재 값을 그대로 실어 보내야 한다.** 형식 검증(`@NotBlank`/`@NotNull`)이 완화 분기보다 먼저 돌아서 비우면 400이다.
- **업로드 400이 두 종류다.** 행 단위 오류는 `failedRows`가 담긴 응답이고, 파일 자체 거부(구 영문 템플릿·헤더 불일치·확장자·크기 초과)는 `data` 없는 `ApiResponse.fail(message)`다. 미리보기 모달이 둘을 구분해 표시해야 한다.
- **결과 상태 한글 라벨은 API로 내려오지 않는다.** 프론트 상수 맵이 백엔드 `StageResultStatusLabels`(대기/합격/불합격/보류/결시/철회)와 글자까지 같아야 엑셀 드롭다운과 화면 배지가 일치한다. `api-contract.md`에 경고를 남겼다.
- **`previousStageResultStatus`는 "바로 앞 stageOrder 단계"의 결과다.** 상태를 보지 않으므로 앞 단계가 미사용 READY면 열 전체가 비고, "직전 합격 여부"로 해석해 필터를 만들면 어긋난다.
- **`results/export`는 영문 12열 그대로**라 새 6개 필드가 없고 업로드 소스로도 쓸 수 없다.
- **`previousStageResultStatus`는 소급해서 바뀔 수 있다.** 발표 완료 단계보다 앞 순서로 READY 단계를 새로 만들거나 옮기면 백엔드가 막지 않는다. §3.6의 순서 규칙(신규 = max + 10, READY는 "맨 뒤로"만)을 프론트가 지켜야 한다. 저장되지 않는 표시값이라 데이터 손상은 없다.
- **테스트 작성 시 주의:** 업로드 템플릿은 SXSSF inline string으로 기록된다. `XSSFWorkbook`으로 열어 `setCellValue`로 편집하면 값이 조용히 무시되어 테스트가 거짓 통과한다. 편집은 `removeCell` 후 `createCell`로 한다.

## 12. S2에서 내린 결정

- **스텝퍼 부제에서 대상 수를 뺐다.** 단계 목록 API에 결과 건수가 없고 결과는 선택 단계만 로드한다. 부제는 "상태 · 발표일"로 한정했고, 대상 수는 선택 단계의 배너에만 나온다(§11 첫 항목의 결정).
- **카운트 카드에서 철회를 뺐다.** 대개 0건이라 카드 한 칸을 쓸 값어치가 없다. 결과 필터 셀렉트로는 고를 수 있다.
- **수험번호 링크는 새 탭으로 연다.** 판정 중 목록을 잃지 않게 한다. 미저장 변경이 있어도 이탈 확인이 뜨지 않는다.
- **엑셀·정정·단계 설정 버튼은 렌더하지 않는다.** 눌러서 아무 일도 안 일어나는 버튼을 두지 않는다. S3·S4에서 같은 자리에 붙인다.
- **단계 0건 공고의 빈 상태는 임시 문구다.** "단계 설정 화면은 준비 중입니다."로 두고, S4에서 드로어를 여는 버튼으로 바꾼다.
- **발표 차단 사유가 셋이다.** 설계 §3.1은 "대기 0건"만 적었으나, 백엔드 `validateStageResultsReadyForAnnounce`가 **결과 0건도 거부**한다("IN_PROGRESS + 결과 0건"은 다른 관리자가 초기화 없이 시작하면 도달 가능). 공고 미게시·대기 잔여·결과 0건 세 사유를 computed 하나로 모아 툴팁·비활성·배너 문구가 같은 출처를 쓰게 했다. 전형 시작도 같은 방식으로 사유를 노출한다.
- **명령 실패 시 단계·결과를 재조회한다.** 가드 실패의 가장 흔한 원인이 "화면이 stale"(다른 관리자가 먼저 전이시킴, 공고 게시 취소)이라, 재조회하지 않으면 배너가 서버와 어긋난 채 같은 실패가 반복된다.
- **일괄 적용은 "지금 보이는 선택 행"에만 건다.** 필터로 가려진 행이 선택된 채 남아 있으면 사용자가 보지 못하는 행에 판정이 적용된다. 배지 숫자와 적용 대상을 모두 필터 통과 행으로 통일했고, 선택 자체는 지우지 않아 필터를 되돌리면 살아난다.
- **코멘트를 가공하지 않는다.** `a-input`의 `change`는 키 입력마다 발생하고 controlled input이라, 부모가 `trim()` 등으로 바꿔 되돌려주면 한글 IME 조합이 깨진다. 빈 문자열 → null 변환만 그리드가 하고 본체는 받은 값을 그대로 버퍼에 담는다.
- **결과 로드 실패와 미조회를 구분한다.** 둘 다 결과 0건이지만 문구가 다르고, 실패 쪽에는 재시도 버튼이 붙는다. 저장바를 결과 목록 블록 밖으로 올려, 로드가 실패해도 편집 버퍼를 저장하거나 버릴 수 있다.

### S2가 남긴 것

- **본체 뷰가 761줄이다.** 계획서 목표(200~350줄)를 넘었지만 프로젝트 기준선(`Application.vue` 725줄, `AdminFaqManageView.vue` 653줄) 안이다. 분리 가능한 덩어리는 라이프사이클 명령 + 상태 표현 computed 약 200줄이고 경계가 이미 깨끗하다. **S3 착수 직전에 `useStageLifecycle` 컴포저블로 뺀다** — 지금 빼면 ref 배관만 늘고, S3가 엑셀·정정으로 +150~250줄을 얹으면 그때는 분리가 필수가 된다.

- **`src/types/jobPosting.ts`와 `src/types/admin/jobPosting.ts`에 `AdminJobPostingListItem`이 동명으로 두 벌 있고, 후자는 파일 안에서 두 번 선언되어 선언 병합된다.** `getJobPostings()`가 실제로 반환하는 것은 전자다. 이 슬라이스가 만든 문제가 아니며 별도 작업으로 분리했다.

## 13. S3에서 내린 결정

- **라이프사이클을 `useStageLifecycle` 컴포저블로 뺐다.** S2 리뷰 권고대로 S3 착수 직전에 순수 이동으로 처리했다. 본체는 763줄에서 639줄로 줄었고, 엑셀·정정을 얹은 뒤에도 721줄이다. S4의 단계 설정 드로어는 이 컴포저블의 `reloadStageAndResults`를 그대로 재사용하면 된다 — 단계 목록 재조회, 선택 단계 복원, 결과 재조회, URL 동기화가 이미 다 들어 있다.
- **템플릿 다운로드 버튼을 배너가 아니라 업로드 모달 안에 뒀다.** 사용자가 "엑셀 업로드"를 누르면 그 자리에서 템플릿을 받고 바로 올릴 수 있다. 배너 버튼 수를 늘리지 않는다.
- **엑셀 버튼을 배너 액션에 뒀다(§4.4의 툴바가 아니라).** §4.3과 §4.4가 서로 다른 위치를 말하는데, 라이프사이클 버튼과 같은 줄에 두는 §4.3 쪽을 택했다. 단계 상태에 따라 나타나고 사라지는 버튼끼리 모여 있는 편이 읽기 쉽다.
- **엑셀 업로드 진입 시 미저장 판정을 "차단"하지 않고 "확인 후 버리고 진행"으로 했다.** §3.3 초안은 차단이었으나, 화면의 다른 이탈 경로(단계 전환·공고 전환·발표)가 전부 확인 후 진행이라 그쪽에 맞췄다.
- **commit 거부(400·409) 응답의 `data`에서 `failedRows`를 꺼내 표에 그린다.** 백엔드가 거부하면서도 행별 결과를 담아 주기 때문이다. 파일 자체가 거부되는 경우(구 템플릿·확장자·크기)는 `data`가 없어 문구만 보여준다. 두 경로를 가르는 것이 업로드 모달의 핵심이다.
- **거부 후에는 요약 칩을 commit 결과에서 읽는다.** preview 값을 그대로 쓰면 "오류 0"이라 표시하면서 표에는 빨간 오류 행이 깔리는 모순이 생긴다. `REJECTED_VALIDATION`은 preview가 오류 0이었을 때만 도달하는 경로라 실제로 발생한다.
- **거부 후 "미변경 행도 보기" 스위치를 잠근다.** 거부 결과에는 실패 행만 담겨 스위치를 켜도 반응이 없어 고장난 것처럼 보인다. 라벨도 "실패 행만 표시 중"으로 바꾼다.
- **미변경 행의 값 열은 "변경 없음"으로 표시한다.** 백엔드가 `UNCHANGED` 행에는 `diff`를 채우지 않아 `-`만 나오는데, 그러면 "데이터 없음"으로 읽힌다. 단 **판정 기준은 `diff`의 유무가 아니라 행 상태다** — `ERROR` 행도 `diff`가 null이라, `diff === null`로 가르면 파싱에 실패한 행에까지 "변경 없음"이 찍혀 문제 없는 행으로 오독된다. `UNCHANGED`일 때만 새 문구를 쓰고 `ERROR`·`STALE`은 `-`를 유지한다.
- **엑셀 왕복 네 호출이 같은 타임아웃 상수를 쓴다.** 다운로드도 백엔드가 xlsx를 전부 만든 뒤에야 응답을 시작하므로, 업로드에만 긴 타임아웃을 주면 대상자가 많은 단계에서 다운로드가 기본 10초에 끊긴다.
- **정정 이력은 바뀐 항목만 골라 보여준다.** 상태·점수·코멘트를 각각 비교해 달라진 것만 잇는다. 정정의 상당수가 점수만 바뀌는 경우인데 상태만 보여주면 "합격 → 합격"이 되어 무엇이 바뀌었는지 알 수 없다.
- **이력 조회 실패를 "이력 없음"과 구분한다.** 정정 이력은 감사 성격이라, 조회가 실패했는데 "정정된 적 없음"으로 읽히면 안 된다.

### S3가 남긴 것

- **모달의 `stageId` 정합성이 마스크에 기대고 있다.** 업로드·정정 모달은 제출 시점에 `props.stageId`를 실시간으로 읽는다. 지금은 `a-modal` 마스크가 스텝퍼와 공고 셀렉트를 막아 열린 채로 단계가 바뀔 수 없지만, 이건 코드에 기록되지 않은 전제다. **S4의 단계 설정 드로어에서 마스크를 끄면 이 전제가 조용히 깨진다.**
- **READY 단계에는 엑셀 경로가 없다.** 다운로드는 발표·마감에서만, 업로드는 진행 중에만 뜬다. 백엔드 export에는 단계 상태 가드가 없으므로 순수 UI 결정이다. 다만 `results/export`는 영문 12열 레거시 시트라 §5.1이 추가한 근무지·지원구분·최종학력·직전 단계가 실리지 않는다 — READY 명단용으로 붙여도 쓸모가 적다. 필요해지면 버튼 추가가 아니라 export 열 확장(백엔드)이 올바른 해법이다.
- **`fileDownload.saveBlobResponse`가 대개 fallback 파일명을 쓴다.** 백엔드 CORS의 `setExposedHeaders`가 `X-Request-Id`만 노출해 크로스오리진에서는 `Content-Disposition`을 읽을 수 없다. 동작은 정상이지만 서버가 정한 파일명이 전달되지 않는다. 파일명을 서버가 정하게 하려면 노출 헤더 추가가 필요하다.
- **같은 원인의 기존 결함이 지원현황 조회에 있다.** `ApplicationStatus.vue`의 경력기술서 다운로드가 `Content-Disposition` 부재를 가드하지 않아 `TypeError`로 실패한다. 이 슬라이스 범위 밖이라 별도 작업으로 분리했다.

## 14. S4에서 내린 결정

- **드래그 대신 위/아래 버튼을 쓴다.** 드래그는 라이브러리가 필요한데 `AGENTS.md`가 새 의존성 추가를 막고, 단계가 3~5개라 버튼으로 충분하다.
- **순서 조작이 두 갈래다.** 백엔드 `reorder`가 **공고의 모든 단계를 빠짐없이** 요구하고 **전 단계가 READY**여야 하기 때문이다. 전부 READY면 위/아래 이동 후 `reorder` 1회, 시작된 단계가 있으면 READY 행을 "맨 뒤로"만 보내고 `update`로 처리한다. §3.6이 예로 든 "1차 면접 진행 중에 2차를 추가하고 최종을 뒤로" 시나리오를 이걸로 커버한다.
- **저장은 삭제 → 수정 → 생성 → 순서 순으로 돈다.** 삭제를 먼저 해야 순서·최종단계 중복 검증에 걸리지 않는다. 수정을 생성보다 먼저 해야, 기존 행이 최종단계를 내려놓기 전에 신규 행이 최종단계를 요구해 400이 나는 일이 없다. 수정 안에서도 **최종단계를 내려놓는 행을 먼저** 보낸다 — 배열상 뒤 행이 최종단계를 넘겨받으면 순서대로 보낼 때 유일성 검증에 걸린다.
- **기존 행의 순서는 원본 값을 그대로 보낸다.** 화면 배열 위치로 다시 매기면 손대지 않은 진행 중·발표 완료 행까지 "순서 바뀜"으로 판정돼 수정 대상이 되고 400이 난다. 신규 행과 "맨 뒤로" 행만 `max + 10`을 받는다.
- **생성 응답의 id를 즉시 draft에 기록한다.** 신규 행이 `id === null`인 채로 남으면 `reorder` 항목에서 빠져 "모든 단계 포함" 규칙을 위반한다. 부분 실패 후 재저장할 때 같은 단계를 두 번 만들지 않는 효과도 있다.
- **잠긴 행이 최종단계를 쥐고 있으면 토글을 막는다.** 진행 중 단계가 최종단계인데 READY 행에 체크하면, 잠긴 행의 값이 바뀌어 그 행이 수정 대상이 되고 400이 난다. 백엔드에서도 옮길 수 없는 상태이므로 화면에서 미리 막는 편이 정직하다.
- **부분 실패 시에도 드로어를 닫는다.** 열어 두면 부모 재조회가 편집 내용을 덮고, 재조회까지 실패하면 단계가 있는데 "등록된 전형 단계가 없습니다"로 보인다. 오류 문구가 몇 건 반영됐는지 알려주므로 사용자는 다시 열어 이어서 작업하면 된다.
- **드로어 마스크를 켠 채로 둔다.** S3가 남긴 전제다 — 업로드·정정 모달이 제출 시점에 현재 단계를 실시간으로 읽어, 마스크가 스텝퍼와 공고 셀렉트를 막는 데 정합성이 걸려 있다.
- **공고 상세의 "전형 단계" 버튼은 공고 상태와 무관하게 보인다.** 공고를 마감해도 단계 상태는 그대로라 진행 중 단계의 **판정은** 계속 가능하기 때문이다(`StageResultService.validateEditable`이 단계 상태만 본다). 다만 판정 결과를 **발표할 수는 없다** — 아래 "남긴 것" 참조. 단계 설정 드로어는 마감 공고에서 읽기 전용이다.
- **최종 단계가 정확히 1개가 아니면 경고한다.** 백엔드 `RetentionEligibilityService.evaluate`가 `finalStages.size() != 1`이면 `INVALID_STAGE_CONFIGURATION`으로 판정해 **그 공고의 지원서가 개인정보 파기 대상에서 영구 제외**된다. 신규 행 기본값이 `finalStage: false`라 체크하지 않고 저장하는 게 자연스러운 흐름이고, 화면에 드러나지 않는 실패라 리텐션 드라이런 리포트에서만 발견된다. 이 드로어가 단계를 만드는 유일한 UI이므로 상시 배너 + 저장 시 확인으로 막는다. 저장 자체를 차단하지는 않는다 — 단계를 여러 번에 나눠 만드는 흐름을 끊지 않기 위해서다.

### S4가 남긴 것

- **대상자를 불러온 READY 단계를 지우면 FK 제약 위반이 난다.** `StageResultService.initialize`가 READY에서도 허용되는데 `StageService.delete`는 단계 상태만 보고 바로 지우고, `Stage`에 `StageResult` cascade가 없다. 프론트에서 막을 방법이 없어 별도 작업으로 분리했다. 백엔드가 삭제를 거부하거나 결과를 함께 지우도록 결정해야 한다.
- **메뉴 등록이 남아 있다.** `/admin/stage-results`는 관리자 메뉴 관리 화면에서 등록해야 사이드바에 뜬다. 코드 변경이 아니라 운영 작업이다. 등록 전에는 URL 직접 입력이나 공고 상세·지원서 설정 현황판의 버튼으로만 도달한다.
- **단계 이름에 앞뒤 공백이 있는 기존 데이터가 있으면 진행 중 단계 수정이 막힌다.** 드로어가 저장 시 `trim()`을 하므로 잠긴 필드가 "바뀐 것"으로 판정된다. 발생 가능성이 낮아 분기를 넣지 않았다.
- **공고를 마감하면 남은 단계가 교착에 빠진다(백엔드 결함).** `JobPostingStatus.CLOSED`는 종착 상태라 되돌릴 수 없는데, `StageService.validateJobPostingPublishedForCommand`가 시작·발표·마감을 모두 PUBLISHED로 제한하고 `validateJobPostingEditable`이 단계 생성·수정·삭제·순서를 CLOSED에서 막는다. 결과적으로 **마감 공고의 진행 중 단계는 판정은 되지만 발표도 마감도 삭제도 영원히 불가**하다. 프론트는 툴팁을 갈라 "마감된 공고라 전형 단계를 더 진행할 수 없습니다."로 정직하게 안내하는 선에서 멈췄다. 근본 해결은 백엔드가 마감 공고에서도 진행 중 단계의 발표·마감을 허용하거나, 공고 마감 시 잔여 단계를 정리하도록 정하는 것이다.
- **단계 삭제가 실패하면 그 드로어 세션의 다른 편집이 전부 유실된다.** 저장이 삭제부터 돌기 때문이다. 별도 작업으로 분리한 FK 결함(대상자를 불러온 READY 단계 삭제)이 고쳐지기 전까지, 사용자에게 보이는 증상은 "삭제가 안 된다"가 아니라 "저장이 통째로 날아갔다"이다.
- **2단계 이후 대상자에 직전 단계 결과 필터가 없다.** `initialize`가 공고의 제출 완료 지원서 전부를 대상자로 넣고, 발표는 대기 0건을 요구한다. 1단계 불합격자까지 전원 판정해야 한다. 그리드에 직전 단계 결과 열은 있지만 필터는 §11 결정대로 넣지 않았다.
- **설계서 §4.8과 구현이 네 곳 다르다.** 드로어 폭 520px → 560px, 최종 단계 라디오 → 스위치, 푸터 "변경 요약" 미구현, 잠금 행 회색 배경 미구현. 기능에는 영향이 없다.
- **공고 목록 조회가 실패하면 헤더만 남은 빈 화면이 되고 재시도 버튼이 없다.** 단계·결과 조회 실패에는 재시도가 있는데 공고 목록만 비대칭이다.
