Recruit Backend - Phase 03k

ApplicationFormConfig Use/Required Policy Split Design

Design Complete Generated: 2026-05-22

Executive Summary

This phase defines how application form section usage and final-submit requiredness should be separated.

The recommendation is to keep existing useXxx fields for visibility and section API access, and add explicit requireXxx fields for submit-blocking and dashboard required-readiness policy.

Review update: requireXxx must not be exposed in request or response payloads before submit and dashboard policies also use it. The recommended Phase 03k-1 is now an end-to-end policy change.

Implementation note: the completed Phase 03k-1 was later narrowed by instruction.md to a public read-only compatibility slice. It adds applicationFormRequiredPolicy to public job posting responses, but it does not implement the target requireXxx fields, schema migration, submit validator conversion, or dashboard completion conversion described by this design.

No Java source, test source, DB migration, runtime API behavior, security configuration, SMS/email, or LDAP behavior is changed in this design phase.

Current Problem

ApplicationFormConfig currently has only seven useXxx flags. Those flags decide section visibility and section API access, but some of them also decide final-submit requiredness and dashboard required readiness.

This makes optional-but-visible sections difficult to support. For example, education may need to be shown and editable without blocking final submit.

AreaCurrent BehaviorIssue
EducationuseEducation=true requires at least one row at submit.Cannot show optional education.
CareeruseCareer=true requires profile/type and row policy.Cannot show optional career.
MilitaryuseMilitary=true requires row/type-specific data.Cannot show optional military.
Certificate/Language/Award/GapEnabled sections are optional guidance only.Cannot make them submit-required.
DashboardMirrors current submit validator assumptions.Required and optional groups are coupled to use flags.

Proposed Policy

useXxx

  • Controls applicant screen visibility.
  • Controls applicant section save/read API access.
  • Controls whether a section can appear in admin/public form config.
  • Does not by itself mean submit-required after the required-policy implementation.

requireXxx

  • Controls submit-blocking validation.
  • Controls dashboard required-missing groups.
  • Controls required completion counts and submit-blocking issue count.
  • Requires the matching useXxx=true.

Review Fixes

Contract Safety Updated

Do not ship a phase where public/admin responses say requireEducation=false while final submit still blocks because useEducation=true. The implementation slice that exposes requireXxx must also convert submit validation and dashboard readiness.

Validation

Requests with requireXxx=true and matching useXxx=false should be rejected with a 400-equivalent validation failure. Silent coercion is not recommended because it hides admin configuration mistakes.

Attachment Decision

Deferred
