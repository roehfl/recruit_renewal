파기의 마지막 조각 — 첨부 바이너리 삭제 saga(①②③) 를 execute 흐름에 통합. ① item 트랜잭션에서 첨부 PII 제거(filenameHash HMAC → originalFileName placeholder) + BINARY_DELETE_PENDING 마킹, ② 트랜잭션 밖 멱등 물리 삭제 + 존재 재확인 (이미 없음 = 성공), ③ REQUIRES_NEW 확정 — 성공 = BINARY_DELETED(storagePath null·binaryDeletedAt), 전부 소멸 확인 시에만 JobApplication/item 최종 PURGED 승격(purgedAt). 실패 = BINARY_DELETE_FAILED 유지 + batch PARTIAL_FAILED(9e reconciliation 대상). 2. 완료 범위

A 상태 재정의(1단계)

  • +SOFT_DELETED·BINARY_DELETE_PENDING/DELETED/FAILED (legacy DELETED 병존)
  • markDeleted() → SOFT_DELETED · 전 사용처 동일 취급(목록/활성/health scan)
  • 의미 집합: HIDDEN_FROM_LISTING / BINARY_OUTSTANDING

B saga ① (item tx)

  • 첨부 PII(§6): filenameHash HMAC(원문 제거 전 계산) → placeholder, deletedBy/사유 null, createdBy bulk
  • 모든 첨부 행 적용 + outstanding 은 PENDING 마킹

C saga ②③ + 승격

  • 멱등 deleteIfExists + exists() 재확인 · invalid/예외 = 실패
  • 전부 소멸 확인 시에만 PURGED 승격(promoteToPurged — fail-loud)
  • 실패: FAILED 유지(경로 보존) + binaryDeleteFailedCount + PARTIAL_FAILED
  • ②③ 사이 crash = "파일 소멸+DB pending"(설계상 안전 — 9e 승격)

D 집계/관측

  • batch binary_delete_failed_count 컬럼 + metadata/응답 전파
  • coarse 감사(PURGE_EXECUTE)에 포함
