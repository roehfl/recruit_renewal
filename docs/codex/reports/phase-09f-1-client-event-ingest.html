1. 요약

Phase 09f(지원자 화면 진단 로그)의 첫 슬라이스. 수집(ingest) 파이프라인 기반만 구현했다 — 지원자 화면 오류/체크포인트를 POST /api/client-events로 수집하고 client_event_log 테이블에 저장한다.

관리자 조회 API는 09f-3, retention cleanup 스케줄러는 09f-4로 이월. 프론트엔드 연동은 별도 FE 프로젝트(09f-2)에서 진행.
설계 편차 4건: 정적 팩토리 네이밍 변경, 정규식 \p{Cntrl}+, @Autowired 추가, 엔티티 주석 보강 — 모두 컴파일/런타임 정확성을 위한 변경. Known Limitations 항목 참조.

7. 검증 및 비즈니스 규칙

DTO 레벨 (@Valid)

필드규칙
eventType / severity / source@NotNull
clientSessionId / clientEventId@NotBlank + ^[A-Za-z0-9\-]{8,80}$
message@Size(max=200) + ^[A-Za-z0-9 _.:\-]*$ — safe code만
기타 문자열 필드@Size(max=N) — 컬럼 길이 동일

서비스 레벨

  • source 검증: APPLICANT_WEB만 허용 → 그 외 즉시 400
  • rate limit 3단: ip → ip+session → principal(인증 시)
  • 중복 선확인: existsBy → 저장 없이 duplicate 반환
  • metadata sanitize: exact allowlist + 금지 key + value 타입/길이 검증
  • 서버 추출값 강제: ip/ua/receivedAt/ingestCorrelationId는 서비스에서만 채움
  • principalHash: HMAC_SHA256(secret, "CLIENT_PRINCIPAL:"+username) — 원문 미저장
  • message 마스킹: 7자리+ 연속 숫자 → *
  • routePath/apiPath: query string(? 이후) 제거

엔티티 레벨

  • unique constraint: (client_session_id, client_event_id) — race 최종 방어
  • validateRequired: 6개 필수 필드 null/blank 검사 → InvalidClientEventLogException

10. Known Limitations

설계 편차 4건
  1. ClientEventLogIngestResponse 팩토리 네이밍: 플랜의 accepted()/duplicate()/disabled()가 Java record 컴포넌트 접근자와 충돌해 컴파일 불가. ofAccepted/ofDuplicate/ofDisabled로 변경.
  2. sanitize 정규식 \p{Cntrl}+: 연속 제어문자를 공백 1개로 collapse하도록 + 추가(플랜 \p{Cntrl} 대비).
  3. ClientEventRateLimiter @Autowired: 다중 생성자 환경에서 Spring 주입 생성자 판단 실패 해결.
  4. 엔티티 주석 보강: message/ipAddress/userAgent 3개 필드 Javadoc 추가(Task 2 리뷰 반영).
기능 제한 6건
  • rate limit이 @Valid 이후 적용: malformed request flood는 카운터 미집계(Bean Validation에서 먼저 거부).
  • stackSummary 자유 문자열: 현재 검증 없이 수집. 조회 시 ROLE_PRIVACY_ADMIN 전용 예정(09f-3).
  • ipAddress/userAgent 원문 저장: 조회 API(09f-3)에서 ROLE_PRIVACY_ADMIN 게이팅 예정.
  • retention 미구현: yaml 설정 블록만 존재, cleanup 로직은 09f-4.
  • in-memory rate limiter: 서버 재시작 시 초기화, 멀티 인스턴스 미공유. Redis 전환은 별도 phase.
  • reverse proxy 배치 시 ip 단 한계: getRemoteAddr() 기반이라 proxy 뒤에서는 전 사용자가 proxy IP를 공유 — 1차 ip 한도(300/분)가 사이트 전체 상한이 됨. 운영 배치 시 server.forward-headers-strategy=framework 정렬 또는 ip 한도 환경변수 상향 필요.
