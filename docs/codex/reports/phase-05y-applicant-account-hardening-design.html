Phase 05y — Applicant Account Hardening

신영증권 채용 Renewal 백엔드 · 결정-독립 슬라이스 설계 · 2026-06-05
설계 완료 구현 미착수 Phase 09b 선행

1. Executive Summary

지원자 loginId 정책(이메일 = loginId vs 별도 ID)이 미결정인 상태에서, 어느 안이 채택되어도 그대로 유효한 계정 기능만 선별해 설계했다. 핵심은 ① 현재 코드에 실재하는 loginId 무결성 결함 수정(임직원-지원자 loginId 충돌 시 로그인 영구 장애), ② 가입 화면용 이메일 중복체크 API, ③ 지원자 비밀번호/전화번호 변경 API다. 내부 인증 계약(loginId + password)은 두 안 모두 동일하므로 본 슬라이스는 결정과 무관하게 안전하다. 구현 완료 후 Phase 09b 진행에 영향이 없다.

2. 결정-독립성 분석

두 안(이메일=loginId / 별도 ID) 모두 로그인 API, findUserByLoginId 조회, 세션 principal이 loginId 기반으로 동일하다. 분기는 가입 request 구성·중복체크 API 구성·이메일 변경 의미 세 곳뿐이다.

3. 수정 대상 결함 (현재 코드 실재)

3.1 loginId 중복체크 범위 결함. 로그인 해석은 UserRepository.findUserByLoginId()로 users 테이블 전체에서 일어나는데, 가입 중복체크는 ApplicantRepository.existsByLoginId()로 Applicant 서브타입만 본다. 지원자가 기존 임직원(LDAP JIT)의 loginId로 가입하면 체크를 통과하고, 이후 findUserByLoginId가 2건을 반환해 해당 loginId의 지원자/임직원 모두 로그인 영구 장애가 된다.
3.2 User.loginId DB 유니크 제약 부재. email/ciHash와 달리 loginId에는 DB 제약이 없어 동시 요청 race를 막지 못한다. 동시 JIT 중복 Employee row 생성 경로의 backstop도 없다.
3.3 DB 제약 위반 응답 포맷 결함. DataIntegrityViolationException 핸들러가 없어 race 시 500 + Spring 기본 에러 포맷(ApiResponse 아님)으로 응답한다. → 409 + generic 메시지로 정비.

4. Scope Cards

Scope A loginId 무결성

  • User.loginId에 unique = true
  • UserRepository.existsByLoginId 신설
  • signUp 중복체크 User 레벨 전환
  • 운영 수동 DDL(유니크 인덱스)
  • nullable=false는 후속(픽스처 영향)

Scope B 이메일 중복체크

  • GET /auth/applicants/check-email
  • permitAll(명시 등록) · advisory 전용
  • signUp과 동일 정규화(trim) 재사용
  • 응답: { available: boolean } 만

Scope C 비밀번호 변경

  • POST /applicant/account/password
  • 현재 비밀번호 확인 필수
  • 새 비밀번호 = 현재와 동일 거부
  • BCrypt 인코딩 · 본인 세션 유지

Scope D 전화번호 변경

  • POST /applicant/account/phone-number
  • 가입과 동일 검증(NotBlank, max 30)
  • trim 후 저장

Scope E 횡단 보강

  • DataIntegrityViolationException → 409 (응답 generic + 원인은 warn 로그)
  • Applicant.changePassword/changePhoneNumber 의미 메서드

Out of Scope

  • check-login-id · 이메일 변경 · email 필수화 (결정-의존)
  • 아이디 찾기 · NICE 본인인증 · rate limiting
  • ActivityLog 계측(9b 이후 스윕)
  • name/ci 변경 · 임직원 정보 변경
  • permitAll → allowlist 전환(별도 슬라이스)
  • email lowercase 정규화(별도 검토)
  • User.loginId nullable=false(후속)

POST /applicant/account/phone-number ROLE_APPLICANT 전화번호 변경 ApiResponse<Void>

인가 경로

/applicant/account/**는 기존 requestMatchers("/api/applicant/**").hasAuthority("ROLE_APPLICANT")에 이미 포함된다. 신규 네임스페이스를 만들면 anyRequest().permitAll() fall-through로 matcher 누락 시 무인증 공개되는 위험이 있으나, 기존 보호 네임스페이스 재사용으로 이 위험을 구조적으로 제거했다. 심층 방어로 CurrentApplicantService가 미인증 401 / 비지원자 403을 한 번 더 보장한다.

7. Validation / 비즈니스 규칙

#규칙실패 응답
1loginId 중복체크는 users 테이블 전체(임직원 포함) 범위로 수행400 "이미 사용 중인 아이디입니다."
2check-email은 signUp과 동일 정규화(trim) 후 existsByEmail 판정형식 오류 400 (ConstraintViolation)
3check-email은 advisory — 최종 권위는 signUp 재검증 + DB unique—
4비밀번호 변경은 현재 비밀번호 일치 필수400 "현재 비밀번호가 일치하지 않습니다."
5새 비밀번호는 현재 비밀번호와 달라야 함400 "새 비밀번호가 현재 비밀번호와 달라야 합니다."
6새 비밀번호 8~100자, BCrypt 인코딩 저장400 (Bean Validation)
7전화번호 NotBlank, max 30, trim 저장400 (Bean Validation)
8DB 제약 위반은 409 + generic 메시지(제약명/SQL 응답 비노출, 원인은 warn 서버 로그 기록 — 전 엔드포인트 적용이므로 구현 시 회귀 영향 점검)409 "이미 처리되었거나 중복된 데이터입니다."
9name / ci는 변경 API로 열지 않음(본인인증 산출물)—

9. Remaining Issues

구분내용
보안check-email은 enumeration 벡터 — rate limiting/CAPTCHA 미적용(05x 한계 승계), 운영 전 검토. signUp 실패 메시지도 동일 표면을 이미 보유(신규 표면 아님)
보안currentPassword 검증 시도 횟수 제한 없음 · 전화번호 변경 재확인/변경 알림 없음(MessageBatch 실발송 전 후속) · CSRF disabled는 기존 공통 posture이나 비밀번호 변경은 재검토 시 우선 대상
정규화email 대소문자 구분 비교(trim만) — lowercase 도입은 기존 데이터와 함께 별도 검토
세션비밀번호 변경 시 타 세션 무효화 없음(세션 레지스트리 부재)
감사비밀번호/연락처 변경 ActivityLog 계측 보류 — 9b 이후 계측 스윕에서 APPLICANT_PASSWORD_CHANGE 등 추가
결정 대기loginId 정책(이메일 vs 별도 ID) — 가입 화면 프론트 작업 전 timebox 권장

10. Next Phase Recommendation

구현 순서: Scope A + E-1(결함 수정 묶음) → B(check-email) → C/D(계정 변경) + E-2 → 문서/리포트 갱신. 단일 슬라이스 크기. 구현 완료 후 Phase 09b(로그 흡수 + 관리자 변경 audit + read API) 진행 — 본 슬라이스는 audit 파이프라인을 건드리지 않으므로 9b에 영향이 없다. loginId 정책 결정 후 추가 비용은 어느 안이든 소규모다 (안 1: signUp loginId=email + email 필수화 / 안 2: check-login-id API 추가).
