Phase 03i-4 - Attachment Delete / Orphan Cleanup / Admin Repair Design

Design Completed Generated 2026-05-20

Executive Summary

Phase 03i-4 is a documentation-only design phase for attachment delete, orphan cleanup, and admin repair policy after upload and download were implemented. No Java source, tests, security config, build files, YAML, schema, or runtime APIs are changed.

The recommended lifecycle decision is soft delete: keep the DB row, add a future DELETED physical file state, exclude deleted rows from normal metadata lists, and delete physical files after the DB transaction commits.

The phase can move forward to a narrow implementation: applicant DRAFT delete plus admin delete with required reason. Cleanup, repair, and audit history remain separate phases.

Recommended Policy

Use a soft lifecycle state, not hard delete, as the default. A later implementation should add DELETED to PhysicalFileStatus, exclude deleted rows from normal applicant/admin metadata lists, and reject deleted rows from download with controlled 404. ORPHANED should not be a DB enum because orphan physical files have no DB row.

Delete commands should also return 404 for rows that are already DELETED. Admin delete requires a reason, and Phase 03i-4-2 should persist that reason on ApplicationAttachment through minimal delete audit fields. A separate ApplicationAttachmentDeletionHistory table remains deferred.

Transaction / Compensation Strategy

StepPolicy
ValidationCheck actor, ownership/role, application state, attachment/application match, and admin reason.
DB stateInside the transaction, mark the row DELETED instead of hard deleting it.
Physical fileDelete after DB commit using the stored relative key captured before the state change.
Physical delete failureDo not roll back the committed DB delete; log cleanup work for orphan cleanup.
Missing file during deleteTreat idempotently as already absent; do not expose paths.

Orphan Cleanup

  • Start with dry-run only.
  • Detect files under storage root without active DB references.
  • Detect DELETED rows whose physical files still exist.
  • Prefer quarantine/move before permanent delete when operations can support it.
  • Never escape the configured storage root.

Admin Repair

  • Detect STORED rows with missing physical files.
  • Do not auto-mark MISSING during user download.
  • Defer mark-missing and repair commands.
  • Require audit for any repair that reattaches or changes evidence.

Phase 03i-5 Connection

Required attachment and dashboard readiness checks must count only active usable rows. For physical-file requirements, only STORED rows should satisfy readiness; METADATA_ONLY, MISSING, and DELETED rows must not pass a required file rule. Orphan physical files never satisfy readiness because they have no active DB row.

Phase 03i-5 should reuse the active-row filtering introduced by delete implementation instead of creating separate visibility rules.
